### 0.2 用語の定義

| 用語 | 意味 |
|---|---|
| **タイプ（Game Type）** | `voxel` または `fps`。シミュレーションの根本的なパラダイム |
| **Sim Profile** | タイプごとのシミュレーション実装（移動・衝突・ワールド表現・スナップショット内容） |
| **ゲームモード（Game Mode）** | ルールの単位。1つのタイプに属する。例: `voxel-bedwars`, `fps-ffa` |
| **ルーム（Room）** | 1つのゲームモードのインスタンス。プレイヤーが所属する単位 |
| **ゲームノード（Game Node）** | ルームをホストする Bun プロセス。1プロセス = 1 CPUコア |
| **マッチメイカー** | ルーム一覧の提供と入室チケット発行を行うステートレスHTTPサービス |
| **ハブ（Hub）** | プレイヤーがルームを閲覧・参加するWeb UI |
| **ティック（Tick）** | サーバのシミュレーション更新1回 |
| **スナップショット** | サーバ→クライアントの状態同期パケット |

## 1. プロダクト定義

### 1.1 作るもの

ブラウザで動作するマルチプレイヤーゲームプラットフォーム。

- **ハブ**から、稼働中のルームを一覧・検索して参加できる
- ルームは**2つのタイプ**のいずれかに属する
  - `voxel` — bloxd.io 的。編集可能なボクセル世界。建築・サバイバル・ミニゲーム
  - `fps` — Krunker.io 的。静的なアリーナマップ。高速な射撃戦
- 各タイプに**複数のゲームモード**が存在する（タイプが2つであって、ゲームが2つではない）
- 将来的にユーザーが独自のゲームモードを作成できる（UGC）

### 1.2 ゲームモードの想定例

```
voxel タイプ
  ├ voxel-creative     自由建築、PvP無効
  ├ voxel-bedwars      チーム戦、ベッド破壊、資源収集
  ├ voxel-survival     PvE、体力・空腹・Mob
  ├ voxel-parkour      アスレチック、タイムアタック
  └ voxel-skywars      島スタート、中央資源

fps タイプ
  ├ fps-ffa            全員が敵
  ├ fps-tdm            チームデスマッチ
  ├ fps-parkour        射撃なし、移動タイムアタック
  ├ fps-gungame        キルごとに武器変化
  └ fps-search         ラウンド制、リスポーンなし
```

### 1.3 なぜ「統合された単一の移動モデル」にしないのか

v1 設計では「ボクセル＋FPS移動の単一モデル」を検討したが、**却下する**。

理由:

- **物理特性が根本的に異なる。** ボクセルは AABB 対 グリッド、FPSはカプセル 対 三角形メッシュ。統合すると両方が中途半端になる
- **座標範囲が違う。** ボクセル世界は数千〜数万ブロック四方、FPSアリーナは 200m 四方。位置の量子化パラメータが2桁違う
- **ティックレートの最適解が違う。** ボクセルは 20〜30Hz で十分、FPSは 60Hz が必要
- **スナップショットの内容が違う。** ボクセルはブロック差分が主、FPSは弾道と姿勢が主

代わりに **プラットフォーム層を完全に共有し、シミュレーション層だけを差し替える**。これが本設計の中核。

## 2. レイヤーアーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│ L3  ゲームモード層                                             │
│     voxel-bedwars / voxel-creative / fps-ffa / fps-tdm ...    │
│     → GameModeDefinition を export するだけ                    │
│     → 所属タイプを宣言する                                      │
├──────────────────────────────────────────────────────────────┤
│ L2  Sim Profile 層  ★ここだけがタイプごとに分岐                 │
│  ┌───────────────────────┬───────────────────────┐          │
│  │ VoxelProfile          │ FpsProfile            │          │
│  │ ・チャンク管理         │ ・静的マップ + BVH     │          │
│  │ ・voxel-physics-engine│ ・カプセル移動         │          │
│  │ ・ブロック操作         │ ・ヒットスキャン       │          │
│  │ ・i32 座標            │ ・i16 座標            │          │
│  │ ・20-30Hz sim         │ ・60Hz sim            │          │
│  └───────────────────────┴───────────────────────┘          │
├──────────────────────────────────────────────────────────────┤
│ L1  エンジンコア層  ★タイプ非依存                              │
│     Room / TickScheduler / PlayerRegistry / InputQueue        │
│     GameModeRuntime / RateLimiter / ctx 実装                  │
├──────────────────────────────────────────────────────────────┤
│ L0  プラットフォーム層  ★タイプ非依存                           │
│     プロトコル framing / Transport / 認証 / 座席予約           │
│     マッチメイカー / Redis台帳 / ハブUI / プロフィール / チャット │
└──────────────────────────────────────────────────────────────┘
```

**依存の向きは常に下向き。** L2 は L1 を知ってよいが、L1 は L2 を知らない（インターフェース経由でのみ呼ぶ）。L0 は L2 の存在を一切知らない。

### 2.1 タイプ追加のコスト

この設計では、3つ目のタイプ（例: `racing`）を追加するときに触るのは L2 と L3 だけになる。L0/L1 は無変更。**この性質が保たれているかどうかが、設計が正しいかの判定基準**。

実装中に「L1 に `if (type === 'voxel')` を書きたくなった」ら、それは L1/L2 の境界設計を間違えたサイン。インターフェースを見直すこと。

## 4. 中核となる型定義

### 4.1 タイプとプロファイル

```ts
// packages/shared-types/src/index.ts

export type GameType = 'voxel' | 'fps';

/** タイプごとの固定パラメータ。実行時に変更不可 */
export interface TypeSpec {
  readonly type: GameType;
  /** シミュレーション周波数（Hz）。許可される値のみ */
  readonly simHz: number;
  /** スナップショット送信周波数（Hz） */
  readonly snapshotHz: number;
  /** クライアント入力送信周波数（Hz） */
  readonly inputHz: number;
  /** 位置量子化の方式 */
  readonly posEncoding: 'i16_cm' | 'i32_1_256';
  /** ワールドの最大範囲（メートル、原点からの片側） */
  readonly worldExtent: number;
}

export const TYPE_SPECS: Record<GameType, TypeSpec> = {
  voxel: {
    type: 'voxel',
    simHz: 30,
    snapshotHz: 15,
    inputHz: 30,
    posEncoding: 'i32_1_256',
    worldExtent: 32_768,
  },
  fps: {
    type: 'fps',
    simHz: 60,
    snapshotHz: 30,
    inputHz: 60,
    posEncoding: 'i16_cm',
    worldExtent: 327,
  },
} as const;
```

**`posEncoding` の根拠**

| 方式 | サイズ | 分解能 | 範囲 | 用途 |
|---|---:|---:|---:|---|
| `i16_cm` | 2 B/軸 | 1 cm | ±327.67 m | FPSアリーナ。現行 cod-web と同じ |
| `i32_1_256` | 4 B/軸 | 1/256 m ≈ 3.9 mm | ±8,388,608 m | ボクセル世界 |

ボクセル世界で `i16_cm` を使うと ±327m でオーバーフローする。これは cod-web の既知の制約であり、voxel タイプでは必ず `i32_1_256` を使うこと。

ただしスナップショット内では **AOI 相対座標**を使って圧縮する（§5.5）。

### 4.2 SimProfile インターフェース（L1 ↔ L2 の境界）

これが本設計で**最も重要なインターフェース**。L1 はこれ以外の方法で L2 を呼ばない。

```ts
// packages/engine-core/src/profile/SimProfile.ts

import type { GameType, TypeSpec } from '@app/shared-types';

/** シミュレーション状態。プロファイルごとに中身は異なるが、L1 は不透明に扱う */
export interface SimState { readonly __brand: unique symbol }

/** プレイヤー1人分のシミュレーション実体 */
export interface SimEntity { readonly __brand: unique symbol }

export interface SimProfile<TWorldSpec = unknown> {
  readonly type: GameType;
  readonly spec: TypeSpec;

  // ---- ライフサイクル ----

  /** ワールドを生成・ロードする。ルーム作成時に1回 */
  createWorld(worldSpec: TWorldSpec, seed: number): Promise<SimState>;
  destroyWorld(state: SimState): void;

  // ---- エンティティ ----

  spawnEntity(state: SimState, playerId: number, x: number, y: number, z: number): SimEntity;
  despawnEntity(state: SimState, entity: SimEntity): void;

  // ---- シミュレーション ----

  /**
   * 1ティック分のシミュレーションを進める。
   * ★ この関数はクライアントとサーバで完全に同一のコードでなければならない。
   * ★ 副作用・非決定的要素（Date, Math.random, I/O）を含んではならない。
   */
  step(state: SimState, entity: SimEntity, input: DecodedInput, dtMs: number): void;

  /** ゲームモードのフックを呼ぶ必要があるイベントを回収する */
  drainEvents(state: SimState): SimEvent[];

  // ---- 同期 ----

  /** そのプレイヤーに送るべきスナップショット本体を書き込む */
  writeSnapshot(state: SimState, viewer: SimEntity, w: BinaryWriter): void;

  /** そのプレイヤーに送るべきワールド差分（チャンク等）を書き込む。なければ false */
  writeWorldDelta(state: SimState, viewer: SimEntity, w: BinaryWriter, budgetBytes: number): boolean;

  /** タイプ固有のクライアント→サーバパケットを処理する */
  handleTypedPacket(state: SimState, entity: SimEntity, type: number, r: BinaryReader): void;

  // ---- ゲームモードへ公開する追加 ctx ----

  /** RoomCtx に合成されるタイプ固有メソッド群 */
  extendCtx(state: SimState): Record<string, unknown>;

  // ---- 状態取得（L1 が PlayerRef を組み立てるため） ----

  readPose(entity: SimEntity): Pose;
  writePose(entity: SimEntity, pose: Partial<Pose>): void;
}

export interface Pose {
  x: number; y: number; z: number;
  vx: number; vy: number; vz: number;
  yaw: number; pitch: number;
  onGround: boolean;
}

export interface DecodedInput {
  seq: number;
  moveX: number;   // -1.0 .. 1.0（量子化済みの値を逆量子化したもの）
  moveZ: number;
  yaw: number;
  pitch: number;
  buttons: number; // ビットフラグ
  dtMs: number;
}

export type SimEvent =
  | { kind: 'death'; playerId: number; killerId: number | null; cause: number }
  | { kind: 'damage'; victimId: number; attackerId: number | null; amount: number }
  | { kind: 'blockPlace'; playerId: number; x: number; y: number; z: number; blockId: number }
  | { kind: 'blockBreak'; playerId: number; x: number; y: number; z: number }
  | { kind: 'landed'; playerId: number; impact: number };
```

**設計上の要点**

- `SimState` と `SimEntity` を **branded type** にして、L1 が中身を覗けないようにする
- `drainEvents()` により、L2 は L3（ゲームモード）を直接知らずにイベントを発行できる
- `extendCtx()` により、`ctx.setBlock()` のようなタイプ固有APIを合成できる。L1 はその中身を知らない

### 4.3 ゲームモード定義

```ts
// packages/gamemode-sdk/src/types.ts

export interface GameModeDefinition<T extends GameType = GameType> {
  // ---- メタ情報 ----
  readonly id: string;                 // /^[a-z][a-z0-9-]{2,31}$/
  readonly type: T;                    // ★ 所属タイプ
  readonly displayName: string;        // 表示名（32文字以内）
  readonly description: string;        // 説明（200文字以内）
  readonly version: string;            // semver
  readonly author?: string;

  // ---- ルーム設定 ----
  readonly minPlayers: number;         // 1..64
  readonly maxPlayers: number;         // 1..64
  readonly teams: number;              // 0 = チームなし
  readonly roundTimeSec: number;       // 0 = 無制限

  // ---- ワールド ----
  readonly world: T extends 'voxel' ? VoxelWorldSpec : FpsWorldSpec;

  // ---- 移動調整（エンジンが範囲を検証する） ----
  readonly movement?: MovementTuning;

  // ---- ライフサイクルフック ----
  onRoomCreate?(ctx: Ctx<T>): void;
  onRoomDestroy?(ctx: Ctx<T>): void;
  onRoundStart?(ctx: Ctx<T>): void;
  onRoundEnd?(ctx: Ctx<T>, winnerTeam: number | null): void;

  onPlayerJoin?(ctx: Ctx<T>, p: PlayerRef): void;
  onPlayerLeave?(ctx: Ctx<T>, p: PlayerRef): void;
  onPlayerSpawn?(ctx: Ctx<T>, p: PlayerRef): void;
  onPlayerDeath?(ctx: Ctx<T>, victim: PlayerRef, killer: PlayerRef | null, cause: DeathCause): void;

  /** 戻り値: 実際に適用するダメージ量。false でダメージ無効化 */
  onPlayerDamage?(ctx: Ctx<T>, victim: PlayerRef, attacker: PlayerRef | null, amount: number): number | false;

  onTick?(ctx: Ctx<T>, tick: number, dtMs: number): void;

  onNetworkMessage?(ctx: Ctx<T>, p: PlayerRef, id: string, data: unknown): void;

  // ---- voxel タイプ専用（type が 'voxel' のときのみ有効） ----
  onBlockPlace?(ctx: VoxelCtx, p: PlayerRef, x: number, y: number, z: number, blockId: number): boolean;
  onBlockBreak?(ctx: VoxelCtx, p: PlayerRef, x: number, y: number, z: number): boolean;

  // ---- fps タイプ専用 ----
  onWeaponFire?(ctx: FpsCtx, p: PlayerRef, weaponId: number): boolean;
  onHit?(ctx: FpsCtx, shooter: PlayerRef, victim: PlayerRef, bodyPart: BodyPart, distance: number): number | false;
}

type Ctx<T extends GameType> = T extends 'voxel' ? VoxelCtx : FpsCtx;
```

```ts
  id: 'fps-tdm',
  type: 'fps',
  displayName: 'チームデスマッチ',

  maxPlayers: 16,
  teams: 2,

  world: { mapId: 'warehouse', variant: 'default' },

  onPlayerJoin(ctx, p) {
    // 人数の少ないチームへ自動割り当て
    const counts = [0, 0];
    for (const q of ctx.players) if (q.team >= 0) counts[q.team]++;
    ctx.setTeam(p, counts[0] <= counts[1] ? 0 : 1);
    ctx.showMessage(p, `チーム ${p.team + 1} に参加しました`);
  },

  onPlayerSpawn(ctx, p) {
    const spawns = ctx.getSpawnPoints(p.team);
    const s = spawns[ctx.randomInt(0, spawns.length)];
    ctx.teleport(p, s.x, s.y, s.z, s.yaw, 0);
    ctx.setHealth(p, 100);
    ctx.giveWeapon(p, 1, 90);   // アサルトライフル
    ctx.giveWeapon(p, 20, 24);  // ピストル
  },

  onPlayerDeath(ctx, victim, killer) {
    if (killer && killer.team !== victim.team) {
      ctx.addScore(killer, 100);
      ctx.addTeamScore(killer.team, 1);
      if (ctx.getTeamScore(killer.team) >= SCORE_LIMIT) {
        ctx.endRound(killer.team);
        return;
      }
    }
    ctx.after(ctx.type === 'fps' ? 180 : 90, () => ctx.respawn(victim)); // 3秒 @60Hz
  },

  onHit(ctx, shooter, victim, bodyPart, distance) {
    if (shooter.team === victim.team) return false;  // 同士討ち無効
    const base = { head: 100, body: 34, limb: 22 }[bodyPart];
    const falloff = distance > 40 ? 0.6 : 1.0;
    return Math.floor(base * falloff);
  },
});
```

## 5. ネットワークプロトコル仕様

### 5.1 基本方針

- **手書きバイナリ**。`DataView` によるリトルエンディアン。msgpack や JSON は使わない
- **`BinaryReader` は必ず境界チェックを行う。** 現行 cod-web の `getUint32` が `RangeError` を投げてプロセスが落ちる問題への対策
- **タイプ非依存の framing の上に、タイプ固有のペイロードを載せる**
- **制御メッセージのみ JSON**（頻度が低く、可読性の価値が上回る）
- **トランスポートは WebSocket（TCP）のみ。** UDP 系（WebRTC DataChannel / geckos.io / WebTransport）は現フェーズでは一切使わない。ただし**将来 WebTransport に対応することを目標**とし、そのための設計上の備えを最初から入れておく（§5.8）

### 5.2 パケットタイプ番号

```ts
// packages/protocol/src/constants.ts

export const enum PacketType {
  // ---- 0x00-0x0F: 共通・制御（双方向） ----
  Hello          = 0x00,  // C→S 接続直後、チケット提示
  Welcome        = 0x01,  // S→C 受理、ルーム情報配布
  Reject         = 0x02,  // S→C 拒否、理由コード
  Ping           = 0x03,  // C→S
  Pong           = 0x04,  // S→C
  TimeSync       = 0x05,  // S→C サーバ時刻配布
  Disconnect     = 0x06,  // 双方向

  // ---- 0x10-0x1F: 共通・ゲームプレイ ----
  Input          = 0x10,  // C→S 入力（タイプ非依存の共通部分）
  Snapshot       = 0x11,  // S→C 状態同期
  PlayerJoin     = 0x12,  // S→C
  PlayerLeave    = 0x13,  // S→C
  RoomState      = 0x14,  // S→C 状態遷移・スコア
  Event          = 0x15,  // S→C 死亡・ダメージ・サウンド等
  Chat           = 0x16,  // 双方向

  // ---- 0x20-0x2F: ゲームモード独自メッセージ ----
  ModeMessage    = 0x20,  // 双方向 ctx.send/broadcast

  // ---- 0x40-0x5F: voxel タイプ専用 ----
  ChunkData      = 0x40,  // S→C チャンク本体（断片化）
  ChunkUnload    = 0x41,  // S→C チャンク破棄指示
  BlockDelta     = 0x42,  // S→C ブロック差分
  BlockAction    = 0x43,  // C→S 設置・破壊
  InventoryState = 0x44,  // S→C
  ItemUse        = 0x45,  // C→S

  // ---- 0x60-0x7F: fps タイプ専用 ----
  MapInfo        = 0x60,  // S→C マップID・ハッシュ
  WeaponState    = 0x61,  // S→C 武器・弾数
  FireAction     = 0x62,  // C→S 射撃
  ReloadAction   = 0x63,  // C→S リロード
  HitConfirm     = 0x64,  // S→C ヒットマーカー
  Tracer         = 0x65,  // S→C 他プレイヤーの弾道
}
```

**番号帯を分けている理由**: サーバの `handleMessage` で `type >= 0x40 && type < 0x60` なら voxel プロファイルへ、`>= 0x60` なら fps プロファイルへ、というディスパッチが1行で書ける。L1 はパケットの中身を知らずに L2 へ委譲できる。

### 5.3 共通パケット

#### Hello (0x00) — C→S

接続直後に必ず送る。これ以外のパケットは Welcome 前には受け付けない。

```
オフセット  型      内容
0          u8      type = 0x00
1          u8      protocolVersion（現行 = 1）
2          u16     ticketLen
4          bytes   ticket（マッチメイカー発行の署名付きJWT風トークン, UTF-8）
```

サーバは以下を検証し、失敗したら `Reject` を返して即座に切断する。

- `protocolVersion` が一致するか
- チケットの HMAC 署名が正しいか
- `exp` が未来か（TTL 15秒）
- `roomId` が自ノードに存在するか
- その `seatId` が未使用か

#### Welcome (0x01) — S→C

```
0          u8      type = 0x01
1          u8      gameType   0 = voxel, 1 = fps
2          u16     yourPlayerId
4          u32     randomSeed          // 決定論的乱数のシード
8          f64     serverTimeMs        // クライアント時計との差分計算用
16         u16     tickRateHz          // = TYPE_SPECS[type].simHz
18         u16     snapshotRateHz
20         u16     inputRateHz
22         u16     maxPlayers
24         u16     jsonLen
26         bytes   json（UTF-8）
```

`json` の中身:

```jsonc
{
  "roomId": "TOK:k3h17",
  "mode": { "id": "fps-tdm", "displayName": "チームデスマッチ", "version": "1.0.0" },
  "world": { "mapId": "warehouse", "hash": "sha256:9f2a..." },   // fps
  // または
  "world": { "generator": "islands", "seed": 812371, "size": 256, "height": 128 },  // voxel
  "teams": 2,
  "players": [ { "id": 3, "name": "alice", "team": 0, "score": 400 } ],
  "roundState": "playing",
  "roundRemainingSec": 412
}
```

#### Reject (0x02) — S→C

```
0          u8      type = 0x02
1          u8      reason
2          u16     msgLen
4          bytes   msg（UTF-8, 表示用）
```

| reason | 意味 |
|---:|---|
| 1 | プロトコルバージョン不一致 |
| 2 | チケット無効・期限切れ |
| 3 | ルームが存在しない |
| 4 | ルーム満員 |
| 5 | BAN されている |
| 6 | サーバ再起動中 |

#### Input (0x10) — C→S ★固定長

**このパケットは絶対に固定長 16 バイト**。長さが異なるパケットは即座に切断する。

```
0          u8      type = 0x10
1          u8      _reserved（0固定）
2          u32     seq              // 単調増加。巻き戻し用
6          i8      moveX            // -100..100 → -1.0..1.0
7          i8      moveZ
8          u16     yaw              // 0..65535 → 0..2π
10         i16     pitch            // -16384..16384 → -π/2..π/2
12         u16     buttons          // ビットフラグ
14         u16     dtMs             // このフレームの経過時間（ミリ秒 ×10）
```

`buttons` のビット割り当て:

```
bit 0  jump
bit 1  crouch
bit 2  sprint
bit 3  primary   （射撃 / 破壊）
bit 4  secondary （ADS / 設置）
bit 5  reload / interact
bit 6  weapon slot bit0
bit 7  weapon slot bit1
bit 8  weapon slot bit2
bit 9-15  予約（0固定。非0なら不正クライアントとして記録）
```

**検証（サーバ側、必須）**

```ts
if (buf.byteLength !== 16) { ws.close(1002, 'bad input length'); return; }
if (moveX < -100 || moveX > 100) { ws.close(1002, 'bad moveX'); return; }
if (moveZ < -100 || moveZ > 100) { ws.close(1002, 'bad moveZ'); return; }
if (dtMs > 500) { dtMs = 500; }   // clamp。切断はしない（一時的なフリーズ）
if ((buttons & 0xFC00) !== 0) { flagSuspicious(player); }
```

#### Snapshot (0x11) — S→C

```
0          u8      type = 0x11
1          u8      flags       bit0: フルスナップショット / デルタ
2          u32     tick
6          u32     lastAckedInputSeq   // このクライアントの入力をどこまで処理したか
10         u32     baselineTick        // デルタの基準。full の場合 0
14         u16     entityCount
16         bytes   entities...         // ★ SimProfile.writeSnapshot() が書く
```

`lastAckedInputSeq` を**明示的にフィールドとして持つ**こと。現行 cod-web はこれが曖昧なため、クライアント予測の巻き戻し基準が不安定になっている。

### 5.4 スナップショットのエンティティ表現（タイプ別）

#### fps タイプ（1エンティティ = 17 バイト）

```
0          u16     playerId
2          u8      flags     bit0:alive bit1:crouch bit2:sprint bit3:onGround bit4:reloading
3          i16     x         // 1cm 単位、絶対座標
5          i16     y
7          i16     z
9          i16     vx        // 1cm/s 単位
11         i16     vz
13         u16     yaw
15         i8      pitch     // -128..127 → -π/2..π/2（粗くてよい）
16         u8      health    // 0..255
```

`vy` を送らない: 重力は決定論的なので、`onGround` フラグと位置から補間できる。1バイト削減より実装単純さを優先するなら追加してよい。

#### voxel タイプ（1エンティティ = 15 バイト、AOI相対座標）

```
0          u16     playerId
2          u8      flags     bit0:alive bit1:crouch bit2:sprint bit3:onGround bit4:swimming
3          i16     dx        // ★ ビューアのチャンク原点からの相対位置、1cm 単位
5          i16     dy
7          i16     dz
9          u16     yaw
11         i8      pitch
12         u8      health
13         u16     heldItem  // 手に持っているアイテムID
```

**AOI相対座標が成立する理由**

AOI（§5.7）により、スナップショットに含まれるのはビューアから一定距離内のプレイヤーのみ。その距離を 256m 以内に制限すれば、相対座標は `i16` の ±327m に必ず収まる。これで voxel タイプでも 1エンティティ 15 バイトを実現できる。

スナップショットのヘッダに**ビューアのチャンク原点**を含める必要がある:

```
// voxel タイプの場合、Snapshot ヘッダの後に追加
16         i32     viewerOriginX   // ブロック座標
20         i32     viewerOriginY
24         i32     viewerOriginZ
28         bytes   entities...
```

### 5.5 voxel 専用パケット

#### ChunkData (0x40) — S→C

チャンクサイズは **16 × 16 × 16**（Noa のデフォルトに合わせる）。

```
0          u8      type = 0x40
1          u8      encoding    0=raw, 1=RLE, 2=palette+bitpack
2          i32     chunkX
6          i32     chunkY
10         i32     chunkZ
14         u16     fragmentIndex
16         u16     fragmentCount
18         u32     totalLen        // 全断片を結合した後のペイロード長
22         u16     payloadLen
24         bytes   payload
```

**エンコーディング**

| encoding | 形式 | サイズ例 | 用途 |
|---:|---|---:|---|
| 0 raw | `u16 × 4096` | 8192 B | デバッグ専用 |
| 1 RLE | `(u16 blockId, u16 runLength)` の連続 | 空チャンクで 4 B | 実装が最も簡単。まずこれを作る |
| 2 palette | `u8 paletteLen, u16[] palette, bitpacked indices` | 16種以下で 2048 B | 本命 |

palette エンコーディングのビット幅:

```
paletteLen 1     → 0 bit（全て同じブロック。indices 省略）
paletteLen 2     → 1 bit  → 512 B
paletteLen 3-4   → 2 bit  → 1024 B
paletteLen 5-16  → 4 bit  → 2048 B
paletteLen 17-256→ 8 bit  → 4096 B
paletteLen 257+  → raw にフォールバック
```

最大ボクセルID は **65535**（Noa の制約）なので、palette 要素は `u16` で足りる。

**断片化とレート制限（重要）**

WebSocket は単一の TCP コネクションなので、大きなチャンクを送っている間スナップショットが詰まる（Head-of-Line ブロッキング）。これが「地形読み込み中にカクつく」現象の正体。

対策:

- 1断片の `payloadLen` は **最大 4096 B**
- 1ティックあたりに送る断片は **プレイヤーあたり最大 4 個**（= 16 KB/tick @ 30Hz = 480 KB/s の上限。実際にはさらに絞る）
- バックプレッシャ検出時（`ws.send()` が `-1` を返す）は**チャンク送信を完全に停止**し、スナップショットのみ送る
- チャンクの送信順序は、プレイヤーからの距離が近い順 + 視線方向優先

```ts
// 送信優先度（小さいほど優先）
priority = distanceToPlayer * (isInViewCone ? 1.0 : 2.5);
```

#### BlockDelta (0x42) — S→C

```
0          u8      type = 0x42
1          u8      _reserved
2          u32     seq          // 単調増加。欠落検出用
6          u16     count        // 最大 512
8          bytes   entries...

// entry = 14 バイト
0          i32     x
4          i32     y
8          i32     z
12         u16     blockId
```

クライアントは `seq` の欠落を検出したら `ChunkResync` を要求する。TCP 上では通常発生しないが、将来の WebTransport 移行後は必須になる。

#### BlockAction (0x43) — C→S ★固定長 20 バイト

```
0          u8      type = 0x43
1          u8      action       0=break, 1=place, 2=use
2          u32     inputSeq     // 対応する入力シーケンス（巻き戻し用）
6          i32     x
10         i32     y
14         i32     z
18         u16     blockId      // place のみ有効。他は 0
```

**サーバ側の検証（全て必須。1つでも欠けたらチート可能）**

```ts
// 1. プレイヤーからの距離
const reach = mode.type === 'voxel' ? 5.5 : 0;
if (dist2(player, x, y, z) > reach * reach) return reject('out of reach');

// 2. チャンクがロード済みか
if (!chunkStore.isLoaded(x >> 4, y >> 4, z >> 4)) return reject('chunk not loaded');

// 3. レート制限
if (!rateLimiter.tryConsume(player.id, 'blockAction', 20)) return reject('rate limit');

// 4. インベントリ
if (action === 1 && ctx.countItem(player, blockToItem(blockId)) < 1) return reject('no item');

// 5. 設置先の状態
if (action === 1 && isSolid(getBlock(x, y, z))) return reject('occupied');

// 6. プレイヤーのAABBと干渉しないか
if (action === 1 && aabbIntersectsAnyPlayer(x, y, z)) return reject('would trap player');

// 7. ゲームモードのフック
const hook = action === 1 ? mode.onBlockPlace : mode.onBlockBreak;
if (hook && hook(ctx, playerRef, x, y, z, blockId) === false) return reject('denied by mode');

// 8. blockId の妥当性
if (blockId > 65535 || !registry.isRegistered(blockId)) return reject('unknown block');
```

クライアントは即座に予測適用し、サーバが拒否した場合は `BlockDelta` で元の値が送られてくることで自動的に巻き戻る。**専用の拒否パケットは作らない**（帯域の無駄。差分で十分）。

**サーバ側の検証**

```ts
// 1. クライアント申告位置がサーバ側の履歴と乖離していないか
const serverPos = history.getAt(player, clientTimeMs);
if (dist(serverPos, clientOrigin) > 1.5) flagSuspicious(player);  // 切断はしない

// 2. 連射レート
if (now - lastFire[weaponSlot] < weapon.fireIntervalMs * 0.9) return reject('too fast');

// 3. 弾数
if (ammo[weaponSlot] <= 0) return reject('no ammo');

// 4. 巻き戻し量の上限
```

**巻き戻し当たり判定（Lag Compensation）**

### 5.7 AOI（関心領域）

現行 cod-web は全プレイヤーに全スナップショットを送っており、20人で約 193 KB/s の総帯域を消費する。O(n²) なので 64人では約 2 MB/s になり破綻する。

**タイプ別のAOI戦略**

| タイプ | 手法 | パラメータ |
|---|---|---|
| voxel | チャンクグリッド | 半径 8 チャンク（128m）内のプレイヤーのみ |
| fps | 全員送信 + 距離LOD | マップが小さいため全員送るが、遠距離は更新頻度を落とす |

fps タイプの距離LOD:

```

距離 30-80m : 2回に1回（15Hz）
距離 >  80m : 4回に1回（7.5Hz）
視錐台外    : 4回に1回（音の定位に必要なので完全には切らない）
```

voxel タイプのチャンクグリッド:

```ts
// 各プレイヤーが属するチャンク座標をキーにした Map を毎ティック再構築
// 隣接 17×17×17 チャンク（半径8）内のプレイヤーを収集
const key = (cx << 42) | (cy << 21) | cz;   // BigInt を避けるため実際は文字列キーか Map<number, Map<...>>
```

**測定目標**

| 条件 | 目標帯域（クライアントあたり受信） |
|---|---:|
| fps 16人 | < 20 KB/s |
| fps 32人 | < 35 KB/s |
| voxel 32人（分散） | < 15 KB/s（+ チャンク転送は別枠） |
| voxel 32人（密集） | < 30 KB/s |

### 5.8 トランスポート方針とロードマップ

この節は実装順序に直接影響する。**現在の実装範囲**と**将来の目標**を明確に分けて読むこと。

#### 5.8.1 現在の方針（フェーズ 0〜8 の全期間）

**WebSocket（TCP）のみを使う。**

| 技術 | 現フェーズでの扱い |
|---|---|
| WebSocket over HTTP/1.1（`Bun.serve` + `websocket`） | **これだけを使う** |
| 生 UDP | 使わない（ブラウザからは送れない） |
| WebRTC DataChannel（unreliable / unordered） | **使わない** |
| geckos.io（WebRTC ベースの UDP ライブラリ） | **使わない**。`docs/TECH_SELECTION.md` の記述は破棄（§0.3） |
| WebTransport（HTTP/3 / QUIC） | **今は使わない**。将来の移行目標（§5.8.3） |

理由:

1. **サーバ側の実装が存在しない。** Bun v1.3.14 で `http3: true` による HTTP/3（QUIC）が「Highly experimental」として追加されたが、同リリースノートで **WebSocket over HTTP/3 は未対応（`server.upgrade()` は `false` を返す）**、**WebTransport は別プロジェクト**と明記されている（[Bun v1.3.14 リリースノート](https://bun.com/blog/bun-v1.3.14)）。つまり Bun 上に WebTransport サーバを立てる公式手段が現時点で無い。
2. **WebRTC を選ぶと運用コストが跳ね上がる。** STUN/TURN、ICE、DTLS ハンドシェイク、シグナリングサーバが必要になり、ゲームロジックが1行も進まないうちにインフラ作業に数週間を消費する。
3. **TCP でも目標品質には十分到達できる。** Krunker.io は WebSocket（TCP）で 30Hz 以上のティックレートを実現しており、bloxd.io も同様に TCP 上で動作している。ボトルネックはトランスポートではなく、AOI・デルタ圧縮・予測・補間の実装品質側にある。
4. **測定してから最適化する。** UDP に移って改善するのは「パケットロス時の遅延スパイク」だけ。それが実測で問題になる前に移行するのは早すぎる最適化。

**実装担当者への指示**: トランスポートの選択について議論や再検討を始めないこと。§5.8.3 の移行条件が満たされるまで WebSocket 固定。

#### 5.8.2 TCP の弱点をアプリ層で緩和する

TCP の主要な問題は **HOL（Head-of-Line）ブロッキング**。1つの大きなメッセージが後続のスナップショットを詰まらせる。UDP に逃げずに、以下で対処する。

| 対策 | 内容 | 参照 |
|---|---|---|
| チャンク断片化 | チャンク本体を 8 KB 以下の断片に分割し、1ティックあたりの送信量に上限を設ける | §5.5 |
| 送信優先度 | スナップショット > イベント > ブロック差分 > チャンク転送。低優先度はティック予算内に収まる分だけ送る | §6 |
| `perMessageDeflate: false` | 圧縮は CPU とレイテンシを増やすだけ。バイナリは既に密 | §6.1 |
| バックプレッシャ監視 | `ws.send()` の戻り値が `-1` なら送信を止める。`0` は接続異常として扱う（[Bun WebSocket ドキュメント](https://bun.com/docs/runtime/http/websockets)） | §6.1 |
| `ws.cork()` | 同一ティックの複数メッセージを1つの TCP セグメントにまとめる | §6.1 |
| 補間遅延 | パケット間隔 × 2（fps 66ms / voxel 134ms）。TCP の再送スパイクをここで吸収する | §8 |

#### 5.8.3 WebTransport への移行を前提とした設計上の備え

**将来的に WebTransport（HTTP/3 / QUIC）へ対応することを目標とする。** そのため、今のうちから以下を守る。これらは WebSocket 実装にとっても無害または有益なものだけを選んである。

**(a) `NetTransport` 抽象を絶対に破らない**

クライアント側は `apps/web/src/net/` に以下の抽象を置き、ゲームコードは `WebSocket` オブジェクトに直接触れない。

```ts
// apps/web/src/net/transport.ts

/** 論理チャネル。WebSocket 実装では単一TCPストリームに多重化される。
 *  WebTransport 実装では別々の Stream / Datagram にマップされる。 */
export const enum Channel {
  /** 順序保証・信頼性必須。Hello/Welcome/RoomState/Chat/BlockDelta */
  Reliable  = 0,
  /** 最新だけが重要。落ちてもよい。Input/Snapshot */
  Unreliable = 1,
  /** 大容量・低優先度。ChunkData */
  Bulk      = 2,
}

export interface NetTransport {
  connect(url: string, ticket: string): Promise<void>;
  /** payload は呼び出し側が所有権を放棄する（実装は同期的に送るか、コピーする） */
  send(channel: Channel, payload: ArrayBufferView): void;
  /** 受信コールバック。channel は送信側が指定した値が復元される */
  onMessage(cb: (channel: Channel, data: DataView) => void): void;
  onClose(cb: (code: number, reason: string) => void): void;
  close(code?: number, reason?: string): void;
  /** 送信待ちバイト数。WebSocket 実装は ws.bufferedAmount、
   *  WebTransport 実装は writer の内部状態から算出 */
  readonly bufferedAmount: number;
  readonly kind: "websocket" | "webtransport";
}
```

実装は2つ用意する予定。現時点では `WebSocketTransport` のみを書く。

```
apps/web/src/net/
  transport.ts              # 上記インタフェース（今書く）
  websocket-transport.ts    # 実装（今書く）
  webtransport.ts           # 空ファイルも作らない。フェーズ9で追加
```

**禁止事項**: ゲームコードやプロトコルパーサから `WebSocket`、`ws.readyState`、`ws.binaryType` などを直接参照しないこと。参照箇所が1つでもあると移行時に全体を読み直すことになる。Biome の `noRestrictedImports` で `apps/web/src/net/websocket-transport.ts` 以外からの直接利用を禁止する。

**(b) `Channel` の区分を今から守る**

WebSocket 実装では `Channel` は**実質的に何もしない**（すべて同じ TCP ストリームに流れ、順序は保証される）。それでも `send()` の第1引数として必ず正しい値を渡す。WebTransport 移行時に、`Reliable` → 双方向ストリーム、`Unreliable` → Datagram、`Bulk` → 別の単方向ストリーム、という機械的な対応付けだけで済むようにするため。

チャネル番号は WebSocket 実装ではフレーム先頭1バイトに載せる。オーバーヘッドは 1 バイト/メッセージで、`ws.cork()` 併用時は実測で無視できる。

**(c) `seq` による欠落検出を最初から入れる**

`BlockDelta`（§5.5）と `Snapshot` には連番 `seq` を持たせる。TCP では欠落は起きないので、**現在このコードパスは実質デッドコードになる**。それでも書く。理由は、WebTransport の Datagram に移した瞬間に欠落が現実に起きるため、そのときに欠落検出とリカバリ（`ChunkResync` 要求、baseline 再取得）を後から入れるのは実装難易度が跳ね上がるから。

テストでは「人為的にパケットを落とすモックトランスポート」を用意し、`seq` 欠落パスを CI で通し続ける（§10）。これがあると移行時の検証が一気に楽になる。

**(d) 冪等性と「最新だけが正しい」設計を守る**

- `Snapshot` は**それ単体で状態を復元できる**か、`baseline seq` を明示的に参照すること。「直前のスナップショットが必ず届いている」という暗黙の前提を置かない
- `Input` は再送されても副作用が二重に発生しないこと（`tick` 番号で冪等に処理する）
- `BlockAction` などの操作系は、サーバが受理した結果を `BlockDelta` として権威的に返す。クライアントは自分の送信結果を前提にしない

**(e) メッセージサイズの上限を守る**

QUIC Datagram は経路 MTU に制限され、実用上 **1200 バイト以下**が安全圏。したがって:

| メッセージ | 現在の上限方針 |
|---|---|
| `Input` | 16 バイト固定（§5.3）。問題なし |
| `Snapshot` | **1200 バイトを超えたら分割する**設計にしておく。fps 32人 × 17B = 544B なので通常は収まる。AOI で絞れば voxel も収まる |
| `ChunkData` | もともと断片化前提。`Bulk` チャネル（= 将来はストリーム）なので MTU 制約は受けない |
| `Event` / `Tracer` | 1メッセージ1イベント。複数まとめる場合は 1200 バイトで打ち切る |

**(f) HTTP/1.1 依存の認証フローを持ち込まない**

入室チケットは **`Hello` パケットのペイロードとして送る**（§5.3）。Cookie、`Sec-WebSocket-Protocol` ヘッダ、URL クエリ文字列に認証情報を載せない。WebTransport はハンドシェイクの形が違うため、ハンドシェイク層に認証を寄せると移行時に作り直しになる。

#### 5.8.4 移行の判断条件

以下が**すべて**満たされたときに、フェーズ9として WebTransport 対応を検討する。

1. Bun が WebTransport サーバ API を安定版として提供している（または Rust/Go 製のエッジプロセスを別途運用する判断が下されている）
2. 実測で「TCP 再送に起因する遅延スパイク」がプレイ体験の主要なボトルネックとして特定されている（§11 の計測で示す）
3. WebSocket 版を主要トランスポートとして維持できる（ブラウザ・ネットワーク環境によっては WebTransport が使えないため、**フォールバックは恒久的に必須**）

条件2が重要。AOI もデルタ圧縮も未実装の段階で「UDP にすれば速くなる」と考えるのは誤り。トランスポート変更で改善するのはロス時のスパイクだけで、帯域とティック予算は1バイトも改善しない。

#### 5.8.5 参考: WebTransport の現状

- 仕様と API: [WebTransport API（MDN）](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)
- Bun の HTTP/3 実装状況と制約: [Bun v1.3.14 リリースノート](https://bun.com/blog/bun-v1.3.14)
- ブラウザ側は Chromium 系では利用可能だが、**Safari の対応状況が採用の律速になる**。実装前に必ず最新の対応表を確認すること

|---:|---|---|

### 6.2 Room の実装

```ts
// packages/engine-core/src/Room.ts

export class Room {
  readonly id: string;
  readonly type: GameType;
  readonly mode: GameModeDefinition;
  private readonly profile: SimProfile;
  private readonly state: SimState;
  private readonly players = new PlayerRegistry();
  private readonly rng: DeterministicRng;
  private readonly rateLimiter = new RateLimiter();
  private readonly ctx: BaseCtx;

  private tick = 0;
  private nextTickAt = 0;
  private readonly tickIntervalMs: number;

  /** 単一の共有タイマーから呼ばれる。Room 自身は setInterval を持たない */
  tickIfDue(nowMs: number): void {
    if (nowMs < this.nextTickAt) return;

    // 遅延が大きい場合、追いつこうとせずスキップする（スパイラルオブデス回避）
    const behind = nowMs - this.nextTickAt;
    if (behind > this.tickIntervalMs * 5) {
      this.nextTickAt = nowMs + this.tickIntervalMs;
      this.metrics.skippedTicks++;
    } else {
      this.nextTickAt += this.tickIntervalMs;
    }

    this.doTick();
  }

  private doTick(): void {
    const t0 = performance.now();
    this.tick++;

    // 1. 入力を消費してシミュレーション
    for (const p of this.players) {
      const input = p.inputQueue.dequeue(this.tick);
      this.profile.step(this.state, p.entity, input, this.tickIntervalMs);
      p.lastAckedInputSeq = input.seq;
    }

    // 2. 巻き戻し用に位置を記録
    this.lagComp.record(this.tick, this.players);

    // 3. Sim が発行したイベントをゲームモードへ
    for (const ev of this.profile.drainEvents(this.state)) {
      this.runtime.dispatch(ev);
    }

    // 4. ティックタイマー
    this.timers.advance(this.tick);

    // 5. ゲームモードの onTick
    this.runtime.callTick(this.tick, this.tickIntervalMs);

    // 6. スナップショット送信（snapshotHz に応じて間引く）
    if (this.tick % this.snapshotDivisor === 0) {
      this.sendSnapshots();
    }

    // 7. ワールド差分（チャンク等）
    this.sendWorldDeltas();

    const elapsed = performance.now() - t0;
    this.metrics.recordTickTime(elapsed);
    if (elapsed > this.tickIntervalMs) this.metrics.overrunTicks++;
  }

  private sendSnapshots(): void {
    for (const p of this.players) {
      if (p.backpressured) continue;              // バックプレッシャ中はスキップ

      const w = this.scratchWriter;                // ★ 事前確保。毎回 new しない
      w.reset();
      w.u8(PacketType.Snapshot);
      w.u8(0);
      w.u32(this.tick);
      w.u32(p.lastAckedInputSeq);
      w.u32(p.baselineTick);
      const countPos = w.reserveU16();
      this.profile.writeSnapshot(this.state, p.entity, w);
      w.patchU16(countPos, this.entitiesWritten);

      // ★ slice() を使わない。subarray はコピーを作らない
      const r = p.ws.send(w.subarray(), false);
      if (r === -1) p.backpressured = true;
      else if (r === 0) this.disconnect(p, 'send failed');
    }
  }
}
```

**ゼロアロケーションの規則**

`doTick()` の中で以下を**絶対に**行わないこと。

- `new` によるオブジェクト生成（事前確保したプールを使う）
- `[]` / `{}` リテラル（`arr.length = 0` で再利用）
- `.slice()` / `.map()` / `.filter()` / `.substr()`（新しい配列・文字列を作る）
- クロージャの生成（起動時に1度だけ作って使い回す）
- `{ x, y, z }` 形式のベクトル返却（`Float32Array` の SoA か、出力引数を使う）

**現行 cod-web の該当バグ**: `buffer.slice(0, bytes)` を送信ごとに呼んでいるため、20人 × 30Hz で毎秒 600 個の `ArrayBuffer` を生成・破棄している。`subarray()` に置き換えること（`subarray` はビューを返すのでコピーが発生しない）。

### 6.3 RoomManager と TickScheduler

```ts
export class RoomManager {
  private readonly rooms = new Map<string, Room>();
  private timer: Timer | null = null;

  start(): void {
    // ★ ルームごとに setInterval を作らない。5ms の単一タイマーで全ルームを駆動
    this.timer = setInterval(() => {
      const now = performance.now();
      for (const room of this.rooms.values()) {
        try {
          room.tickIfDue(now);
        } catch (e) {
          // ★ 1つのルームの例外が他のルームを巻き込まないよう必ず catch
          this.handleRoomError(room, e);
        }
      }
    }, 5);
  }
}
```

`setInterval(5)` を使う理由: 最速のタイプが 60Hz（16.67ms）なので、5ms 刻みなら最大 5ms のジッタで済む。1ms にすると CPU を無駄に消費する。

### 6.4 入力キューとジッタバッファ

現行 cod-web の `MAX_QUEUED_INPUTS = 120` は単なる上限であり、キューが単調に増える／`idleInput` で発散する問題がある。

```ts
export class InputQueue {
  private readonly buf: DecodedInput[];        // 事前確保したリングバッファ
  private head = 0;
  private tail = 0;

  /** 目標バッファ長（ティック数）。ネットワークジッタに応じて動的に調整 */
  private targetDepth = 2;

  push(input: DecodedInput): boolean {
    if (this.size() >= 32) return false;        // 溢れたら破棄（切断はしない）
    // ...
  }

  dequeue(tick: number): DecodedInput {
    const depth = this.size();

    if (depth === 0) {
      // 入力が届いていない。前回の入力を繰り返す（ボタンは離す）
      this.repeatCount++;
      return this.makeIdleFrom(this.lastInput);
    }

    if (depth > this.targetDepth + 3) {
      // 溜まりすぎ。2個消費して追いつく
      this.consume();
    }

    this.repeatCount = 0;
    return this.consume();
  }

  /** 直近64ティックの depth 分散から targetDepth を再計算 */
  adaptTarget(): void {
    const jitter = stddev(this.depthHistory);
    this.targetDepth = clamp(Math.ceil(1 + jitter * 2), 1, 8);
  }
}
```

**上限超過時の挙動**

| 対象 | 挙動 |
|---|---|
| `Input` パケット長が 16 以外 | **即切断**（コード 1002） |
| 入力レート超過 | 即切断 |
| `ctx.broadcast()` 超過 | `false` を返す（例外を投げない） |
| `ctx.send()` 超過 | `false` を返す |
| `ctx.setBlock()` 超過 | 無視 + 警告ログ |
| `onTick` が 8ms 超を5回連続 | ゲームモードを停止し、ルームを `ended` にして全員に通知 |
| その他のパケットのレート超過 | そのパケットを破棄 |

Krunker の KrunkScript も同じ思想で、`broadcast` はレート超過時に例外ではなく `false` を返す設計になっている。

### 6.6 サーバのメッセージハンドラ（完全形）

```ts
websocket: {
  message(ws, raw) {
    const conn = ws.data as Connection;

    // 1. 文字列は制御メッセージのみ許可
    if (typeof raw === 'string') {
      if (raw.length > 4096) return ws.close(1009, 'text too large');
      return handleControlJson(conn, raw);
    }

    const buf = raw instanceof ArrayBuffer ? new Uint8Array(raw) : raw;

    // 2. ★ 最低長チェック。これがないと getUint8 で落ちる
    if (buf.byteLength < 1) return ws.close(1002, 'empty');

    const type = buf[0];

    // 3. Welcome 前は Hello のみ
    if (!conn.authed && type !== PacketType.Hello) {
      return ws.close(1008, 'not authenticated');
    }

    // 4. ★ 固定長パケットは長さを厳密に検証
    const expected = FIXED_PACKET_SIZES[type];
    if (expected !== undefined && buf.byteLength !== expected) {
      return ws.close(1002, `bad length for 0x${type.toString(16)}`);
    }

    // 5. ★ 全体を try/catch。BinaryReader も内部で境界チェックする
    try {
      const r = new BinaryReader(buf);
      r.skip(1);

      if (type < 0x40) {
        handleCommon(conn, type, r);
      } else if (type < 0x60) {
        if (conn.room.type !== 'voxel') return ws.close(1002, 'wrong type packet');
        conn.room.profile.handleTypedPacket(conn.room.state, conn.entity, type, r);
      } else if (type < 0x80) {
        if (conn.room.type !== 'fps') return ws.close(1002, 'wrong type packet');
        conn.room.profile.handleTypedPacket(conn.room.state, conn.entity, type, r);
      } else {
        return ws.close(1002, 'unknown packet type');
      }
    } catch (e) {
      metrics.packetErrors.inc(type);
      return ws.close(1002, 'malformed packet');
    }
  },
}
```

```ts
export const FIXED_PACKET_SIZES: Record<number, number> = {
  [PacketType.Input]:        16,
  [PacketType.BlockAction]:  20,
  [PacketType.FireAction]:   24,
  [PacketType.ReloadAction]:  6,
  [PacketType.Ping]:         10,
};
```

`BinaryReader` は全ての読み取りメソッドで残りバイト数を検証し、不足なら `ProtocolError` を投げること。

### 7.3 チケット形式

```
v1.<base64url(payload)>.<base64url(hmac-sha256)>
```

```jsonc
// payload
{
  "roomId": "TOK:k3h17",
  "nodeId": "tok-01",
  "seatId": 7,
  "uid": "u_8821",
  "name": "alice",
  "iat": 1757001234,
  "exp": 1757001249
}
```

HMAC の鍵はマッチメイカーとゲームノードで共有する環境変数（`TICKET_SECRET`）。**ゲームノードはマッチメイカーへ問い合わせずに検証できる**ため、入室経路にネットワーク往復が増えない。

**座席予約が必須である理由**: これがないと「残り1席の部屋に同時に5人が接続する」競合が必ず発生する。Colyseus も同じ概念（seat reservation）を採用している。

### 7.4 Redis キー設計

| キー | 型 | TTL | 内容 |
|---|---|---:|---|
| `node:{nodeId}` | Hash | 10s | `region`, `wsUrl`, `version`, `cpuLoad`, `currentRooms`, `maxRooms` |
| `nodes:{region}` | Set | — | そのリージョンの nodeId 集合 |
| `room:{roomId}` | Hash | 15s | `nodeId`, `type`, `mode`, `players`, `max`, `state`, `meta` |
| `rooms:{region}:{type}` | ZSet | — | score = 空き人数。空き部屋の高速検索用 |
| `rooms:{region}:{modeId}` | ZSet | — | 同上、モード単位 |
| `seat:{roomId}:{seatId}` | String | 15s | 予約した uid。`SET NX` で原子的に確保 |
| `roomseq:{region}` | String | — | ルームID採番カウンタ |

**座席確保の擬似コード**

```ts
// 1. 空き部屋を探す（空き人数が多い順ではなく、少ない順 = 早く埋める）
const candidates = await redis.zrangebyscore(`rooms:${region}:${modeId}`, 1, '+inf', 'LIMIT', 0, 10);

for (const roomId of candidates) {
  const room = await redis.hgetall(`room:${roomId}`);
  if (!room || room.state === 'ended') continue;

  // 2. 空いている seatId を探して原子的に確保
  for (let seat = 0; seat < Number(room.max); seat++) {
    const ok = await redis.set(`seat:${roomId}:${seat}`, uid, 'NX', 'EX', 15);
    if (ok) return issueTicket(roomId, room.nodeId, seat, uid);
  }
}

// 3. 空きがなければ新規作成
if (createIfNone) return createRoom(...);
throw new Error('no_room_available');
```

ゲームノードは、プレイヤーが実際に接続したら `seat:{roomId}:{seatId}` の TTL を除去（永続化）し、退出したら削除する。15秒の TTL は「チケットを取ったが接続しなかった」ケースの自動回収。

```ts

  pitch += accumDy * sensitivity * 0.0022;
```

### 8.6 クライアント側の予測と補間

```ts
// apps/web/src/net/prediction.ts

class Predictor {
  private readonly pending: DecodedInput[] = [];   // 事前確保したリングバッファ

  /** ローカル入力を即座に適用し、後の巻き戻しに備えて保存 */
  applyLocal(input: DecodedInput): void {
    this.profile.step(this.localState, this.localEntity, input, this.dtMs);
    this.pending.push(input);
  }

  /** サーバのスナップショットで巻き戻し・再適用 */
  reconcile(serverPose: Pose, ackedSeq: number): void {
    // ack 済みの入力を破棄
    while (this.pending.length > 0 && this.pending[0].seq <= ackedSeq) {
      this.pending.shift();   // ★ shift() は O(n)。リングバッファで置き換えること
    }

    const err = dist(this.profile.readPose(this.localEntity), serverPose);
    if (err < RECONCILE_TOLERANCE) return;   // 許容誤差内なら何もしない

    // サーバ位置へスナップし、未 ack の入力を再適用
    this.profile.writePose(this.localEntity, serverPose);
    for (const input of this.pending) {
      this.profile.step(this.localState, this.localEntity, input, this.dtMs);
    }
  }
}

export const RECONCILE_TOLERANCE = { voxel: 0.35, fps: 0.25 } as const;
```

**補間バッファの長さ**

Valve の Source エンジンの解説によれば、20 snapshot/s（50ms間隔）に対して描画時刻を 50ms 戻すのが基本。これは「1パケットロスまで耐えられる最小値」という考え方。

```
補間遅延 = パケット間隔 × 2
```

| タイプ | snapshotHz | パケット間隔 | 既定の補間遅延 |
|---|---:|---:|---:|
| fps | 30 | 33 ms | **66 ms** |
| voxel | 15 | 67 ms | **134 ms** |

現行 cod-web は 30Hz に対して 100ms を使っており、安全側に振りすぎている。66ms に下げるだけで体感が明確に改善する。

さらに、直近のパケット到着ジッタを測って動的に伸縮させるのが理想（`interpolationMs: 'auto'`）。

```ts
// 直近32パケットの到着間隔の標準偏差から算出
const interpMs = clamp(packetIntervalMs * 2 + jitterStddev * 1.5, packetIntervalMs, 250);
```

#### Noa の初期化（クライアント）

```ts
import { Engine as NoaEngine } from 'noa-engine';

const noa = new NoaEngine({
  tickRate: 30,                       // ★ 1秒あたりのティック数（旧APIはms単位だった）
  maxRenderRate: 0,                   // 0 = 無制限（vsync 任せ）
```

**`manuallyControlChunkLoading: true` が必須である理由**

これを有効にしないと、Noa がクライアント側で勝手にワールド生成してしまう。サーバ権威型では**クライアントは地形を生成せず、受信するだけ**でなければならない。有効化した上で、`ChunkData` パケットを受信したときに手動でチャンクをエンジンへ渡す。

**Noa にはネットワーク機能が一切ない。** bloxd.io / CityCraft.io / VoxelSrv は全てネットコードを自前で実装している。Noa が担当するのは「ローカルのボクセル世界＋描画＋物理」まで。

#### 物理（クライアント・サーバ共通）

`voxel-physics-engine` が必要とするのは以下の抽象関数のみで、Babylon にも DOM にも依存しない。**これによりサーバ（Bun）でも同一コードを実行できる。**

```ts
import Physics from 'voxel-physics-engine';

const voxelIsSolid  = (x: number, y: number, z: number) => chunkStore.isSolid(x, y, z);
const voxelIsLiquid = (x: number, y: number, z: number) => chunkStore.isLiquid(x, y, z);

const phys = new Physics({ gravity: [0, -22, 0] }, voxelIsSolid, voxelIsLiquid);

const body = phys.addBody(
  aabb,          // プレイヤーのAABB
  70,            // mass
  0.9,           // friction
  0.0,           // restitution
  1.0,           // gravityMult
  onCollide,     // 衝突コールバック（impacts: vec3）
);
body.autoStep = true;      // 1ブロックの段差を自動で登る
body.airDrag = 0.02;
body.fluidDrag = 0.4;

phys.tick(dtMs);           // ★ 引数はミリ秒
```

主要プロパティ:

| API | 内容 |
|---|---|
| `body.resting[axis]` | 各軸で固体ボクセルに接触しているか（-1 / 0 / 1）。`resting[1] === -1` が接地 |
| `body.onCollide(impacts)` | 地形衝突時のコールバック。`impacts` は各軸のインパルス vec3。バウンス解決前に呼ばれる |
| `body.autoStep` | 1ブロックの障害物を自動でステップ |
| `body.airDrag` / `body.fluidDrag` | 0 で無抵抗、1 で強い抵抗。`>= 0` でグローバル設定を上書き |

**既知の制約**

- **剛体同士の衝突は非対応**（剛体 対 固体ボクセルのみ）。つまり**プレイヤー同士がすり抜ける**
- 立方体でないボクセル形状との衝突は非対応（階段・スラブは AABB 近似になる）

プレイヤー同士の衝突が必要なら、`phys.tick()` の後に自前の AABB 押し出しパスを追加する。これは §15 の未解決事項。

#### ChunkStore

```ts
export class ChunkStore {
  private readonly chunks = new Map<bigint, Uint16Array>();   // 16³ = 4096 要素
  private readonly dirty = new Set<bigint>();

  private key(cx: number, cy: number, cz: number): bigint {
    // 各軸 21 bit（±1,048,576 チャンク = ±16,777,216 ブロック）
    return (BigInt(cx + 0x100000) << 42n) | (BigInt(cy + 0x100000) << 21n) | BigInt(cz + 0x100000);
  }

  getBlock(x: number, y: number, z: number): number {
    const c = this.chunks.get(this.key(x >> 4, y >> 4, z >> 4));
    if (!c) return BLOCK_UNLOADED;
    return c[((y & 15) << 8) | ((z & 15) << 4) | (x & 15)];
  }

  setBlock(x: number, y: number, z: number, id: number): void { /* ... */ }
}
```

**インデックス順序 `(y << 8) | (z << 4) | x`** を採用する理由: Y を最上位にすることで、同じ高さの層が連続配置され、RLE の圧縮率が上がる（地形は水平方向に均質なため）。

#### 決定論の注意

`voxel-physics-engine` は浮動小数点で動作し、ビット単位の決定論は保証されない。以下を守ること（§10 も参照）。

- クライアント・サーバで**完全に同一のコード**を実行する（分岐禁止）
- 入力は必ず量子化 → 逆量子化を経てから `step()` に渡す
- 許容誤差 0.35 を超えたときのみ位置を強制補正する

```ts
// 1. 巻き戻し量を決定（最大 250ms）

const restore = lagComp.rewind(rewindMs);

const worldDist = map.raycast(ox, oy, oz, dx, dy, dz, weapon.range);
```

## 10. 決定論とテスト戦略

### 10.1 決定論の規則（違反は即バグ）

`SimProfile.step()` およびそこから呼ばれる全てのコードで、以下を**禁止**する。

| 禁止事項 | 代替 |
|---|---|
| `Math.random()` | `ctx.random()`（シード付きPRNG） |
| `Date.now()` / `performance.now()` | `ctx.tick` / `ctx.elapsedMs` |
| `setTimeout` / `setInterval` | `ctx.after()` / `ctx.every()` |
| `Array.prototype.sort()`（比較関数なし） | 安定ソートで明示的な比較関数を指定 |
| `Map` / `Set` の反復順序への依存 | ソート済み配列を使う |
| `for...in` によるオブジェクト反復 | 明示的なキー配列 |
| I/O、`fetch`、`fs` | すべて禁止 |
| プラットフォーム依存の数学関数 | 使用する関数を固定し、テストで検証 |

### 10.2 PRNG

```ts
// packages/engine-core/src/DeterministicRng.ts
// xoshiro128** — 高速で品質が十分、状態が 128bit

export class DeterministicRng {
  private s0: number; private s1: number; private s2: number; private s3: number;

  constructor(seed: number) { /* splitmix32 で初期化 */ }

  next(): number { /* 0 <= x < 1 */ }
  nextInt(min: number, max: number): number { /* [min, max) */ }

  /** サーバのシードを welcome で配布し、クライアントも同じ系列を再現する */
  getState(): Uint32Array;
  setState(s: Uint32Array): void;

```

**注意**: 予測に使う乱数と、サーバ専用の乱数（ドロップ抽選など）は**別インスタンス**にすること。混ぜると再生成のたびに系列がずれる。

### 10.3 テスト要件

各フェーズの完了条件に含める。

| テスト種別 | 内容 | 最低ライン |
|---|---|---|
| **量子化ラウンドトリップ** | `encode(decode(encode(x))) === encode(x)` を全フィールドで | 各フィールド 10,000 ケース |
| **決定論** | 同一入力列を2回流して、最終状態のバイト表現が一致すること | 各プロファイル 1,000 ティック × 100 回 |
| **クライアント・サーバ一致** | 同じ入力列をクライアント実装とサーバ実装に流して一致すること | 各プロファイル |
| **プロトコル fuzz** | ランダムなバイト列を `handleMessage` に投げて、プロセスが落ちないこと | 1,000,000 ケース |
| **長さ検証** | 全固定長パケットについて、長さ±1 で必ず切断されること | 全パケット |
| **レート制限** | 各制限が正しく発火し、`false` を返す／切断することの検証 | 全項目 |
| **バックプレッシャ** | `send()` が `-1` を返す状況を再現し、チャンク送信が停止すること | — |
| **GC** | 1,000ティック実行してヒープ増加が 1 MB 未満 | 各プロファイル |
| **AOI** | 目標帯域（§5.7）を満たすこと | 各シナリオ |
| **負荷** | 32人 × 4ルームで、平均ティック時間が予算内に収まること | 各プロファイル |

**決定論テストの実装例**

```ts
test('voxel sim is deterministic', () => {
  const inputs = generateInputSequence(1000, seed);

  const runA = runSimulation(inputs, seed);
  const runB = runSimulation(inputs, seed);

  // ★ 浮動小数点の比較ではなく、量子化後のバイト列で比較する
  expect(serializeState(runA)).toEqual(serializeState(runB));
});
```

## 12. セキュリティ

### 12.1 脅威モデル

| 脅威 | 対策 | 実装フェーズ |

| テレポートハック | 同上。移動量の上限チェック | 2 |
| リーチハック（voxel） | ブロック操作の距離検証（5.5m） | 7 |
| エイムボット | 検出しない（サーバでは原理的に困難）。統計的な異常検知は将来課題 | — |
| ウォールハック | AOI により視界外のプレイヤー情報を送らない（部分的な緩和） | 7 |
| Fake lag | 入力の到着間隔を監視し、極端な場合は警告フラグ | 7 |
| UGC による無限ループ | 実行時間計測と強制中断（QuickJS） | 8 |
| UGC による情報漏洩 | サンドボックス。I/O 完全禁止 | 8 |

### 12.2 クライアント側チート対策の方針

**クライアント側の難読化・改変検出には投資しない。**

Krunker は WASM でJSを実行時生成し、`Function` コンストラクタの `toString()` を検査し、スタックトレースを照合し、XHR でゲームファイルの改変を検出する、という多層の検査を積んでいる。それでも継続的にバイパスされている。

OSS プロジェクトではソースが公開されている前提なので、クライアント側の秘匿は原理的に成立しない。**サーバ権威を徹底することだけが有効な対策**。

具体的には:

- 位置・体力・スコア・所有権はすべてサーバが決定する
- クライアントが送ってよいのは「入力」と「意図」だけ
- ヒット判定はサーバが巻き戻して再計算する（クライアントの申告を信用しない）
- クライアント申告位置とサーバ位置の乖離は記録するが、即座に切断はしない（誤検知が多いため）

### 12.3 プレイヤー保護

- チャットのレート制限（2 msg/s）と文字数制限（200文字）
- 表示名の検証（制御文字・ゼロ幅文字の除去、長さ制限）
- 通報機能とサーバ側ログ保持
- IP ベースのレート制限（マッチメイカー側、Cloudflare で実施）

## 13. UGC 対応（フェーズ8）

### 13.1 サンドボックス

`@sebastianwessel/quickjs` を使用する。WebAssembly 版 QuickJS で、Node.js と Bun の両方で動作する。

移行時に必要な作業は以下のみ。**`RoomCtx` インターフェースは変更しない。**

1. `ctx` の各メソッドを WASM 境界を跨ぐブリッジ関数として再実装する
2. `PlayerRef` を境界を越えるプレーンオブジェクトとしてシリアライズする（すでに `readonly` なので設計変更不要）
3. 実行時間の計測と強制中断を追加する
4. メモリ上限を設定する
5. スクリプトの永続化・配信・バージョニングを実装する

### 13.2 UGC 制限

| 項目 | 制限 |
|---|---|
| スクリプトサイズ | 64 KB（bloxd.io は 16,000 文字） |
| `onTick` 実行時間 | 8 ms |
| ルームあたりのヒープ | 32 MB |
| 使用可能なグローバル | `ctx` のみ。`console` は `ctx.log` へ差し替え |
| `import` | 禁止 |
| `async` / `await` / Promise | 禁止 |
| 正規表現 | 許可するが ReDoS 対策としてタイムアウトを設定 |

### 13.3 配信フロー

```
作者 → エディタでスクリプト作成 → 検証（構文・静的解析）→ 保存
     → 公開申請 → 自動チェック（禁止API・サイズ）→ 公開
     → ハブに表示 → プレイヤーがルーム作成 → ゲームノードがスクリプトを取得して実行
```

ゲームノードはスクリプトをコンテンツハッシュでキャッシュする。同じスクリプトの再取得を避ける。

## 14. 意思決定ログ（ADR）

実装中にこれらを覆したくなった場合、**実装せずにまず人間へ確認すること**。

### ADR-001: タイプごとに Sim Profile を分離する

- **決定**: `voxel` と `fps` で移動・衝突・ワールド表現・座標量子化をすべて分離する
- **却下した案**: 統合された単一の移動モデル
- **理由**: 物理特性・座標範囲・ティックレート・スナップショット内容がすべて異なる。統合すると両方が中途半端になる
- **代償**: L2 のコード量が約2倍になる
- **保証**: L0/L1 は完全に共有されるため、ハブ・マッチメイキング・プロトコル framing・ネットコードの重複はゼロ

### ADR-002: レンダラは自作しない

- **決定**: Babylon.js を使う
- **理由**: bloxd.io は Noa（Babylon.js ベース）、Krunker は Three.js を使っており、**どちらもレンダラを自作していない**。価値はプラットフォーム層にある
- **「自作エンジン」の定義**: L1 + L2 + L3インターフェース。レンダラは含まない

### ADR-003: React Three Fiber を捨てる

- **決定**: 3D空間に React を使わない
- **理由**: ボクセル世界はチャンクメッシュが常時生成・破棄されるため、React の再調整がオーバーヘッドになる。Babylon は命令的APIなのでこの問題が構造的に発生しない
- **React の残す範囲**: ハブUI、HUD、設定画面、メニュー（すべてDOM）

### ADR-004: msgpack ではなく手書きバイナリ

- **決定**: `DataView` による手書きバイナリプロトコル
- **理由**: 入力パケットが 16 バイト固定など、msgpack では実現できないサイズになる。既存資産もある
- **例外**: 制御メッセージ（Welcome の詳細情報、チャット）は JSON。頻度が低く可読性の価値が上回る

### ADR-005: 現在は WebSocket のみ。WebTransport は将来目標

- **決定**: **トランスポートは WebSocket（TCP）のみ**。UDP / WebRTC DataChannel / geckos.io / WebTransport は現フェーズでは実装しない。ただし**将来 WebTransport へ対応することを明示的な目標**とし、`NetTransport` 抽象・`Channel` 区分・`seq` 欠落検出・1200バイト方針・`Hello` ベース認証を最初から入れる（§5.8）
- **理由**: Bun v1.3.14 で HTTP/3（QUIC）が実験的に追加されたが、**WebSocket over HTTP/3 は未対応で `server.upgrade()` は `false` を返し、WebTransport は別プロジェクトとされている**（[Bun v1.3.14 リリースノート](https://bun.com/blog/bun-v1.3.14)）。Bun 上に WebTransport サーバを立てる公式手段が現時点で存在しない。WebRTC を選ぶと STUN/TURN・ICE・シグナリングの運用負担がゲーム実装を止める
- **代替策**: チャンク転送の断片化・送信優先度・`ws.cork()`・補間遅延で HOL ブロッキングを緩和する（§5.5、§5.8.2）
- **再検討条件**: §5.8.4 の3条件をすべて満たしたとき（Bun の安定 API、実測でのスパイク特定、WebSocket フォールバック維持可能）。フェーズ9として着手する
- **恒久的な前提**: WebTransport に移行しても **WebSocket 実装は削除しない**。ブラウザ・ネットワーク環境によって使えないため、フォールバックは永続的に必須

### ADR-006: Havok（Babylon 物理）を使わない

- **決定**: fps タイプは自前BVH + カプセルスイープ、voxel タイプは `voxel-physics-engine`
- **理由**: サーバ（Bun）で同一コードを動かす必要がある。Havok は WASM ロードのコストがあり、サーバでの動作保証もない
- **代償**: 衝突コードを自分で書く必要がある
- **緩和**: FPSのカプセル移動は既知の実装パターンであり、ボクセルは既製ライブラリがそのまま使える

### ADR-007: プレイヤー同士の衝突は当面なし

- **決定**: `voxel-physics-engine` の制約をそのまま受け入れ、プレイヤー同士はすり抜ける
- **理由**: 剛体同士の衝突が非対応。自前で足すと決定論の検証コストが増える
- **再検討**: フェーズ5でゲーム性に問題が出た場合。§15 の未解決事項

### ADR-008: 座席予約を必須にする

- **決定**: マッチメイカーが HMAC 署名付きチケットを発行し、ゲームノードが検証する
- **理由**: これがないと満室ルームへの同時接続で競合する。Colyseus も同じ概念（seat reservation）を採用
- **代償**: マッチメイカーとゲームノードで秘密鍵を共有する運用が必要

### ADR-009: クライアント側チート対策に投資しない

- **決定**: 難読化・改変検出は実装しない。サーバ権威のみ
- **理由**: OSS でソース公開が前提。Krunker が多層の検査を積んでも継続的にバイパスされている実績がある
- **例外**: 統計的な異常検知は将来課題として残す

### ADR-010: 1つ目のゲームモードは雑に作る

- **決定**: `fps-ffa` は最小実装にとどめ、早期に2つ目（`voxel-bedwars`）へ到達する
- **理由**: ゲームモードAPIが正しいかどうかは、2つ目を作るまで原理的に分からない
- **前提**: フェーズ6でAPIを1回作り直すことを計画に含めてある
