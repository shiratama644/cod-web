# 権威サーバー設計（仕様書）

> 位置づけ: Phase 1（ネットワーク）着手前の**設計決定記録（ADR 相当）・仕様書**。
> トランスポート・プロトコル・信頼性の分類は [`networking.md`](./networking.md) が正本。
> コードのディレクトリ・依存方向は [`modules.md`](./modules.md)、ライブラリ候補は [`tech-stack.md`](./tech-stack.md)、設計原則は [`game-engineering-principles.md`](./game-engineering-principles.md) を参照。
> 2026-09-03 の議論で確定した方針をまとめる。

## 1. 目標とスコープ

- Krunker.io 上位互換のブラウザFPS。**権威型サーバー**で状態を確定し、クライアントは予測のみ。
- **マッチ形態（確定）**: Krunker 風の**インスタンスルーム制**。**1 ルームあたり 20〜40 人**、ゲームモードは FFA / TDM を中心とする。
  - 1 ルームの全プレイヤーが互いに見える前提でよく、**初期は AOI（関心範囲による同期待ち）を持たない**。フルルーム・スナップショットを 30Hz で全員にブロードキャストする。
  - 帯域試算: 40 人 × コンパクトなプレイヤー状態（位置/視点/フラグで数10B）≈ 数100B〜1KB/tick。30Hz でも 1 ルームあたり数十KB/s で収まり、20〜40 人規模では AOI 不要。
- **Phase 1 の最小到達点（確定）**: **位置同期（動くプレイヤーがお互いに見える）**。射撃・当たり判定・キル・ラウンド制・購入・マッチメイキングは後続。

## 2. 確定した設計判断（2026-09-03）

| 論点 | 決定 | 理由 |
| :--- | :--- | :--- |
| ルーム形態/規模 | インスタンスルーム、**20〜40 人/ルーム**、FFA/TDM | Krunker 互換。フルスナップショットで十分、初期は AOI 不要 |
| サーバー実装 | **自前の軽量実装（bun `Bun.serve` + ネイティブ WebSocket + 自前ルーム/スナップショット）** | WT/WS・30Hz・msgpackr・独自予測調停に完全適合。薄く掌握できる |
| フレームワーク | **Colyseus ライブラリは使わない**。ルームライフサイクル・seat reservation・固定ステップ netcode の**設計パターンのみ参考** | Colyseus は WS ファーストで独自 schema 同期が 30Hz/msgpackr/WT 方針と二重化。パターンは有用なので自前に取り込む |
| キャラクター物理 | **物理エンジン不使用。three-mesh-bvh でキネマティック・キャラクターコントローラー（疑似リジッドボディ・浮遊カプセル）を自前実装**。マップは **3D Mesh Map（GLTF）の BVH** に衝突・射撃レイを統一。コアは **shared の純粋関数**でクライアント/サーバー共有 | BVH は CPU のみでヘッドレス bun でも動作（作者確認済み）。軽量・決定論的で予測/調停と相性◎。Rapier は動的剛体が要る段階まで不使用 |
| アニメーション | **XState v5 の FSM** で状態遷移（idle/walk/run/jump/fall/crouch/ADS/射撃/リロード）。連続ブレンドはブレンドスペース | サーバーは FSM を持たず権威フラグのみ。アニメはクライアント決定論的再生 |
| 初期トランスポート | **Phase 1 は WebSocket バイナリをエンドツーエンドで先行**（bun ネイティブ WS）。WebTransport は Caddy エッジ終端の経路を検証してから有効化 | bun は WT サーバー未実装（[`networking.md`](./networking.md) §2/§6）。Krunker 自身も WS/TCP。NetTransport 抽象の背後に WT を後挿し。**パケットはバイナリ固定レイアウトなので WS↔WT で共通** |
| WS サーバー基盤 | **bun ネイティブ WebSocket（= uWebSockets コア）**。Node の `uWebSockets.js` パッケージは bun で動作しないため入れない | bun の WS は内部で uWebSockets を使用し、**TCP_NODELAY・pub/sub・backpressure が組込み済み**（bun メンテナ談）。アドオン不要で uWS の低遅延が得られ、bun ランタイム統一を維持 |
| 高頻度シリアライズ | **入力・スナップショットは手動バイナリ固定レイアウト（DataView / ArrayBuffer）で Phase 1 から**。JSON/msgpackr は高頻度パケットには使わない | 40 人スナップショットを **~650B に収め MTU（~1200B）1 データグラム/セグメントで送信**。ゼロアロケ・GC レス。低頻度の信頼イベント（チャット・ルーム・購入、後続）は msgpackr のまま |
| レート構成 | **入力 C→S = 60Hz**（~16ms ごと、毎フレーム級）／**サーバー tick = 30Hz**／**スナップショット S→C = 30Hz**（20〜30Hz の範囲で調整）／描画 60〜120FPS | 入力を 60Hz にして操作レイテンシを半減（上り ~12B×60/s で微小）。サーバーは 30Hz tick で最新入力を消費。スナップショットは帯域飽和防止に 30Hz 上限 |
| バックプレッシャ | サーバーは送信前に**ソケットのバッファ量を監視**し、詰まっているクライアントへは**古いスナップショットをスキップ**して最新のみ送る | TCP の送信キュー詰まりによる遅延累積（HOL）を防止。bun では `ws.send()` の戻り値 / `ws.bufferedAmount`（`backpressureLimit`）で判定 |
| リモート補間 | スナップショットを **50〜100ms の補間バッファ**に溜め、過去 2 フレーム間を Lerp | 20〜30Hz 更新でも 60〜120FPS で滑らかに見える。詰まったらわずかに外挿（extrapolate）で吸収 |

## 3. プロセス/ランタイム構成

```
ブラウザ（client）
  │  ① WebTransport(UDP/443) を試行 → 不可なら ② WebSocket(TCP/443)
  ▼
Caddy（エッジ）  ── TLS 終端。将来 HTTP/3・WebTransport を終端
  │  Phase 1 は WebSocket(TCP) をそのまま bun へリバースプロキシ
  ▼
bun ゲームサーバー（Bun.serve）
  - ネイティブ WebSocket（uWS）で接続処理
  - ルーム管理・30Hz 固定シミュレーション・スナップショット生成
  - ヘッドレ: レンダラー(WebGPU/WebGL)・react・DOM は使わない。
    three の core/math と three-mesh-bvh（いずれも CPU のみ・WebGL 不要）
    で 3D Mesh Map の BVH 衝突を権威計算
  ▲
  │ shared/ の純粋ゲームロジック（キネマティックCC・BVH衝突・ラグ補償計算）
  │   をクライアント予測とサーバー権威の両方から呼ぶ（同一 BVH・同一コード）
```

- **WebTransport の段階的ロールイン**: クライアントは `NetTransport` インターフェース（Phase 0 で境界のみ定義）の実装として WT/WS を持つ。Phase 1 では WS 実装をエンドツーエンドで通し、WT は「Caddy で WT を終端 → bun へ中継する経路（datagrams/streams をどう bun に渡すか）」を別途検証してから切り替える。**WT が使えない間も WS がフォールバックとして本来のゲームプレイを保証**する。
- ゲームサーバーと課金/認証/永続は分離（[`networking.md`](./networking.md) §4.3 の HTTPS API 層）。

## 4. ルームモデルとライフサイクル（Colyseus パターンを自前で）

Colyseus のライフサイクル概念を自前実装に取り入れる（ライブラリは使わない）。

- **Room（ルーム）**: 1 マッチのインスタンス。参加プレイヤー集合・固定 30Hz シム・スナップショット生成・ブロードキャストを持つ。
- ライフサイクル: `onCreate`（ルーム生成・世界ロード）→ `onJoin(playerId)`（参加・初期状態付与）→ `onLeave(playerId)`（離脱・エンティティ除去）→ `onDispose`（ルーム終了・クリーンアップ）。
- **Matchmaking / seat reservation（パターン参考）**: クライアントはまず「参加要求（希望モード/ルーム）」を出し、サーバーが**座席予約（seat reservation）**を発行 → その予約でゲーム接続（WS/WT）を確立、という二段階にすると認証・ルーム割当・再接続が綺麗になる。
  - **Phase 1（位置同期のみ）では**: 起動時の**固定/単一デフォルトルーム**に接続するだけでよい。マッチメイキング・ロビー・seat reservation は後続タスク。
- プレイヤーはサーバーが払い出す `playerId`（ルーム内で一意）を持つ。

## 5. 固定タイムステップ・シミュレーション（権威）

- サーバーは **30Hz 固定 tick**（dt = 1/30s）でルームをシミュレートする（描画とも入力 60Hz とも独立）。60Hz で届く入力は各 tick で最新値を消費する（溜まっていれば最新、無ければ前回値を維持）。
- 移動は **shared の純粋関数**で決定論的に計算する（クライアント予測とサーバー権威が**同一関数・同一 BVH** を呼ぶ）:
  - 入力: 移動入力（前後左右・ジャンプ・しゃがみ等）、視点（yaw/pitch）、ボタン状態。
  - 出力: プレイヤーの位置・速度・接地状態。
  - **物理エンジンは使わない**。**three-mesh-bvh** で**キネマティック・キャラクターコントローラー（疑似リジッドボディ・浮遊カプセル）**を自前実装する:
    - プレイヤーを**カプセル**とし、重力を積分しつつ BVH に対して **shapecast（カプセル vs 三角形）** で地面・壁・坂・段差との衝突を解決する（浮遊高さをスプリング/レイで維持し、坂・階段を自然に登る。定石は pmndrs の BVHEcctrl・three-mesh-bvh 公式の characterController 例）。
    - **マップは 3D Mesh Map（GLTF）**。そのジオメトリから BVH を構築し、衝突も射撃レイも同一 BVH に対して行う。クライアント/サーバーで**同一マップ → 同一 BVH** を持つことで予測と権威が一致する。
  - **ヘッドレス対応**: three-mesh-bvh の BVH 生成・shapecast・raycast は **CPU のみで WebGL を使わない**（作者 gkjohnson 確認済み）。よって bun サーバーでも `three` の core/math（Vector3/Capsule/Geometry 等）と `three-mesh-bvh` を import して同一計算ができる。サーバーはレンダラー（three/webgpu・three の WebGLRenderer）や react/DOM は使わない。
  - 純粋関数の形: `stepPlayer(player: PlayerState, input: InputCommand, dt: number, world: CollisionWorld): PlayerState`（`CollisionWorld` は BVH をラップした衝突世界。副作用を外に出さない）。
  - Rapier 等の本物の剛体エンジンは、投擲物・崩れる動的オブジェクト等が必要になるまで導入しない（プレイヤー移動には不要）。
- サーバーは**移動の妥当性を検証**（速度上限・テレポート/座標ジャンプの棄却・範囲外チェック・BVH 外へのめり込み補正）。不正な移動は補正する。

### 5.1 マップ BVH のビルド時事前生成とヘッドレス読込（資産パイプライン）

マップ BVH は静的でプレイヤー数に依存しないため、**実行時に毎回構築せず事前計算する**のが定石:

- **ビルド時（開発/CI の Node/bun スクリプト）に 1 回だけ BVH を生成**:
  - 3D Mesh Map（GLTF）から衝突プリミティブのジオメトリを取り出し、`new MeshBVH(geometry, {...})` を構築。
  - `MeshBVH.serialize(bvh)` でバイナリ（`{ roots: ArrayBuffer[], index }`）化して書き出す。
  - 格納方法は2案: ①GLTF に**専用拡張（`three_mesh_bvh`）でアクセサとして埋め込む**（1ファイル化、配信がシンプル）、②`.bvh` サイドカーバイナリとしてマップと並べて置く。どちらでも可（Phase 1 のマップ導入時に確定）。
- **ランタイムは deserialize するだけ**:
  - **クライアント**: GLTFLoader でマップを描画用に読み込み、`MeshBVH.deserialize(data, geometry)` で `geometry.boundsTree` を復元。移動 shapecast も射撃 raycast も同じ BVH を使う。
  - **サーバー（ヘッドレス bun）**: GLTFLoader（`window`/`Image` 等のブラウザ API 依存）は使わず、**衝突に必要な最小データ（position + serialize 済み roots/index）だけをバッファから直接読み**、`MeshBVH.deserialize` で復元する。テクスチャ/マテリアル/GLTFLoader は不要。これで**起動はほぼ0秒**で、重いジオメトリ解析をサーバーで行わない。
  - `deserialize` は root バッファを共有（コピー不要）。複数ルーム/ワーカーで同じマップ BVH を共有できる（`useSharedArrayBuffer` 等の選択肢は実装時に検討）。
- **Phase 1 ではマップは平面/簡易ジオメトリ**（GLTF なし）で位置同期を検証し、GLTF マップとこの事前生成パイプラインは**アセット/マップ導入フェーズ**で整える。ただし BVH へのアクセスは最初から「ビルド済み BVH を deserialize で受け取る」境界（`CollisionWorld`）に統一しておくと、後で差し替えが要らない。

### 5.2 同一 BVH の使い回し（移動・射撃・ラグ補償）

- **1 つのマップ BVH を、移動衝突（カプセル shapecast）と銃のヒットスキャン（`bvh.raycast`）で共有する**。別々の衝突構造を持たない。
- ラグ補償（§6.6）の巻き戻しレイ判定も同じ BVH を使う。**マップは静的なので BVH は巻き戻す必要がなく**、巻き戻すのは動的エンティティ（プレイヤー）の位置/姿勢だけ。マップ BVH を共有することで、サーバーの当たり判定・巻き戻し判定の実装コストが下がる。

## 6. パケット設計（位置同期フェーズ）

高頻度パケット（入力・スナップショット）は **手動バイナリ固定レイアウト（DataView / ArrayBuffer）** で作る。JSON / msgpackr は高頻度パケットには使わない（サイズ・GC・MTU のため）。低頻度の信頼イベント（チャット・ルーム管理・購入、後続）は開発速度優先で msgpackr のまま（[`networking.md`](./networking.md) §5）。

**全バイナリパケット共通**: 先頭に **メッセージ種別バイト（`type: uint8`）** を 1B 置く（[`networking.md`](./networking.md) §4.4。WS でも WT datagrams でも共通）。エンディアンは **リトルエンディアン**。パック用バッファはモジュールスコープで確保して再利用し**毎フレーム `new ArrayBuffer` しない**（ゼロアロケーション）。

### 6.1 クライアント → サーバー: Input Packet（**60Hz**・バイナリ・非信頼）

| フィールド | 型 | サイズ | 説明 |
| :--- | :--- | :--- | :--- |
| `seq` | `uint32` | 4B | 入力シーケンス番号。単調増加（予測/調停用） |
| `moveX` / `moveZ` | `int8` ×2 | 2B | 移動入力（-1, 0, 1）。※正規化は float 側で |
| `yaw` | `uint16` | 2B | 水平視点。0〜2π ラジアンを 0〜65535 にマッピング |
| `pitch` | `int8` | 1B | 垂直視点。-π/2〜+π/2 を -128〜127 にマッピング |
| `flags` | `uint8` | 1B | ジャンプ / しゃがみ / ダッシュ等のビットフィールド |
| `dt` | `uint16` | 2B | 前入力からのデルタ（ms）。クライアント側経過時間 |

- 本体 **約 12B** ＋ 先頭の種別 1B。**毎 ~16ms（60Hz）送信**（描画フレームに合わせる、30Hz tick とは独立）。
- パケロスしても次の入力で上書きされる（非信頼で可）。サーバーは 30Hz tick で**最新の入力**を消費する。
- 射撃トリガー等は後続フェーズで flags/別メッセージに追加。

### 6.2 サーバー → クライアント: Snapshot Packet（**30Hz**・バイナリ・非信頼）

**ヘッダ（種別 1B ＋ 8B）**:

| フィールド | 型 | サイズ | 説明 |
| :--- | :--- | :--- | :--- |
| `serverTick` | `uint32` | 4B | サーバー tick 番号 |
| `lastAckSeq` | `uint32` | 4B | そのクライアントについて処理済みの最新 Input `seq`（調停用） |

**各プレイヤー（1 人あたり 16B × 最大 40 人 ＝ 640B）**:

| フィールド | 型 | サイズ | 説明 |
| :--- | :--- | :--- | :--- |
| `playerId` | `uint16` | 2B | ルーム内で一意のプレイヤー ID |
| `x`, `y`, `z` | `int16` ×3 | 6B | 位置を **0.01m 単位の固定小数点**（-327.68〜+327.67m） |
| `vx`, `vy`, `vz` | `int16` ×3 | 6B | 速度（0.01m/s 単位などに固定小数点化）。補間精度・外挿用 |
| `yaw` | `uint16` | 2B | 向き（水平。0〜65535） |

- 合計 **約 1 + 8 + 640 ≈ 649B**（40 人時）。**MTU ~1200B に 1 発で収まり**、TCP フラグメンテーション / UDP 分割が起きず低遅延で到達。
- pitch・isGrounded/crouch 等のフラグが必要なら、1 人あたりに `pitch(int8)` + `flags(uint8)` を 2B 追加しても 40 人で +80B（≈729B）で MTU 内に収まる（Phase 1 では yaw のみでも可）。
- **座標量子化の注意**: 初期マップは固定小数点の範囲（原点から ±327m）に収める。マップが広域化したら **ルーム/マップ原点からの相対オフセット**か、`int32` 化・スケール変更で対応する（後続）。
- **30Hz（20〜30Hz の範囲でチューニング）で全員へブロードキャスト**。初期はフルスナップショット・AOI なし。将来の帯域最適化（差分・量子化強化・AOI）は [`networking.md`](./networking.md) §5 の段階移行に従う。

### 6.3 バックプレッシャ（送信キュー詰まり対策）

- TCP の最大の遅延源は「回線の遅いプレイヤーの送信バッファに未送信パケットが溜まること」。
- サーバーは各スナップショット送信前に **ソケットのバッファ量をチェック**し、閾値（例: ~1KB 程度）を超えていたら**そのクライアントへの今回のスナップショットをスキップ**（次 tick の最新を送る）。
  - bun では `ws.send(data, true)` の戻り値（送信バイト数 / `-1` = バックプレッシャ）または `ws.bufferedAmount`、`Bun.serve` の `backpressureLimit` を使用する（実装フェーズで API を確認）。

### 6.4 予測・調停・補間（ネットモデル詳細）
- **自プレイヤー（ローカル予測）**: 入力を即座に共有移動関数（§6.5 の `applyMovement`）でローカル反映（毎フレーム、delta time）。送信済み入力を `seq` 付きでローカルに保持。
- **調停（Reconciliation）**: スナップショットの `lastAckSeq` までの入力がサーバーに反映済みと分かったら、自プレイヤーを**サーバー確定位置へ補正**し、まだ ack されていない入力（`seq > lastAckSeq`）を先頭から**再適用（Replay）**して現在位置を求める。
- **リモートプレイヤー（補間）**: スナップショットを **50〜100ms のバッファ**に蓄積し、**「現在時刻より約 50ms 過去」をレンダー時刻**として、それを挟む過去 2 フレーム間を Lerp する。パケット揺らぎ/ロスを吸収し、20〜30Hz 更新でも 60〜120FPS で滑らか。バッファが不足した場合は短時間の外挿（extrapolate）で繋ぐ。
- クライアント側の毎フレーム更新は **React state を使わず ref / store の getState** で（[`game-engineering-principles.md`](./game-engineering-principles.md)）。

### 6.5 共有キネマティック移動（クライアント/サーバー同一コード）

予測と権威シミュレーションを完全に一致させるため、移動は **`shared/` の純粋な TS 関数**として実装し、両者が同じものを呼ぶ（[`modules.md`](./modules.md) の shared/sim）。

- 状態 `PlayerState { x, y, z, vx, vy, vz, isGrounded }`、入力 `PlayerInput { moveX, moveZ, yaw, jump, dt }`。
- 処理: ①yaw から移動方向ベクトルを算出し水平速度へ（歩行 SPEED）、②重力とジャンプ（接地時のみ JUMP_FORCE）、③座標を積分、④**カプセルを BVH に shapecast して衝突解決**（地面・壁・坂・段差、浮遊高さの維持）。
  - 衝突世界は `CollisionWorld`（**3D Mesh Map から構築した three-mesh-bvh の BVH** をラップ）として引数で受け取る。初期段階のチュートリアル/スモークでは「`y<=0` の平面マップ＋ BVH」でもよいが、本番は GLTF メッシュの BVH に対して解く。
- **決定論のための注意**: パケット上は量子化（yaw は uint16 等）されるが、移動計算には**デコード後の値を必ず使う**こと（クライアント/サーバーで量子化誤差が同じになるようにする）。BVH は同一マップから同一に構築され、shapecast 結果も両者で一致する前提。
- アニメーションは別系統: **XState v5 のアニメ FSM**（idle/walk/run/jump/fall/crouch…）がクライアントで状態遷移を駆動する（[tech-stack.md](./tech-stack.md) §8）。サーバーは FSM を持たず、接地/移動速度/フラグといった権威状態を送るだけ。
- 参考定数（SPEED=8.0 / GRAVITY=-20.0 / JUMP_FORCE=7.0 や BVHEcctrl の gravity/floatHeight/maxSlope 等）はチューニング対象。

### 6.6 ラグ補償（設計のみ・射撃フェーズで使用）
- サーバーは各プレイヤーの直近 **約100ms の位置/姿勢履歴**を保持する。
- 射撃イベント（後続）が届いたら、**発射者の視点時刻まで当たり判定対象を巻き戻し**てレイ判定 → ダメージを信頼チャネルで確定（[`networking.md`](./networking.md) §3/§4.2）。位置同期フェーズでは履歴バッファの器だけ用意しておく。

## 7. スケール・デプロイ（見通し）

- **1 bun プロセスで多数のルーム**をホスト可能（20〜40 人/ルーム × 複数ルーム）。CPU が詰まったらプロセス/インスタンスを増やす水平スケール。
- ルームはステートフル。インスタンスをまたぐ割当はロビー/マッチメイキング・ディレクタが行い、**座席予約**で特定ルームへ接続させる（Colyseus パターン）。ルーム間の状態共有は原則不要。Redis 等はマッチメイキング/プレゼンス規模が必要になってから。
- エッジは Caddy（TLS。将来 HTTP/3/WT 終端）。静的アセットは CDN。
- このあたりの具体的デプロイ手順は Phase 1 後半〜運用フェーズで `docs/ops/` に整備する。

## 8. Phase 1 への落とし込み（位置同期マイルストン）

Phase 1 のネットワーク初期タスク。デベロッパー提案の 5 ステップを本構成（bun WS）に合わせたもの:

1. **Step 1 接続確立**: bun `Bun.serve`（ネイティブ WebSocket）サーバ起動 ＋ クライアント（R3F）からの WS 接続。ブラウザコンソールに「WebSocket Connected」。NetTransport 抽象の WS 実装として実装（WT はインターフェース維持で後回し）。
2. **Step 2 オフラインキネマティック**: **shared の純粋移動関数** `applyMovement`（§6.5）を作り、クライアント単体で WASD 移動＋カプセルをローカル描画（オフラインで快適に動くこと）。
3. **Step 3 入力送信＆サーバーループ**: クライアントが **Input Packet（バイナリ・60Hz）** を送信。サーバーは **30Hz tick** で `applyMovement` を権威実行（単一デフォルトルーム・参加/離脱）。サーバーログで座標更新を確認。
4. **Step 4 スナップショット＆補間**: サーバーが **Snapshot Packet（バイナリ・30Hz・~650B/40人）** を全員へブロードキャスト（バックプレッシャで詰まりクライアントは間引き）。クライアントは他プレイヤーを **50〜100ms 補間バッファ＋Lerp** で描画。**2 タブ/ブラウザで片方を動かすと他方で滑らかに動くこと**がゴール。
5. **Step 5 調停＆遅延耐性**: クライアント予測＋**調停（`lastAckSeq` まで確定位置に補正し未承認入力を Replay）**。意図的に遅延（100ms 等）を入れ、自分の操作感がオフライン並みに保たれるか検証。

- 検証: 複数クライアント（タブ/ヘッドレス）で互いのプレイヤーが滑らかに動いて見えること。パック/アンパック・`applyMovement`・量子化は純粋関数として **Vitest でユニットテスト**（Sandbox では E2E/実描画不可。パケットの往復は bun サーバをローカル起動したロジックテストで確認）。
- パッキングは `shared/protocol/packer.ts`（バイナリ固定レイアウト・静的バッファ再利用・ゼロアロケ）に集約する。

> 射撃・ラグ補償・マッチメイキング・ルームモード（FFA/TDM の勝敗）・購入・チャット・WT 有効化は、この位置同期が安定してからの後続タスク。

## 9. 残る論点（将来の判断）

- WebTransport を Caddy 終端から bun へどう中継するか（datagrams/streams のバックエンド経路）— WT 有効化フェーズで検証。
- 動的剛体（投擲物・崩れるオブジェクト等）が必要になった場合の剛体エンジン（Rapier 等）要否。プレイヤー移動は three-mesh-bvh のキネマティックCC で固定。
- マッチメイキング/ロビー・再接続・スケール（Redis 等）の具体方式。
- アンチチートの深さ（移動検証は初期から、ダメージ/射撃検証は射撃フェーズ）。
