## 1. 目標と前提

- プロダクト: [Krunker.io](https://krunker.io) にインスパイアされたブラウザFPS（**完全上位互換**）。
- **性能目標**: 「どの端末でも **最低 60FPS**」をフロアとし、**描画は可変フレームレート**（60Hz 端末は 60、120Hz 端末は 120 で動作）。60 は上限ではなく下限。
- **レンダラー**: WebGPU を最優先、WebGPU API 不在時は WebGL2 へ自動フォールバック（WebGL2 を全端末 60FPS の基準ラインとする）。
- サーバーは**権威型（Authoritative）**。クライアントは予測のみ。
- ランタイム: クライアント/ビルドは **bun**、ゲームサーバーも bun を基本とする（構成は §6）。

## 2. トランスポート戦略（確定）

**WebTransport を主経路、WebSocket をフォールバック＆信頼メッセージ経路とする。geckos.io（WebRTC-UDP）は採用しない。**

| 経路 | プロトコル | 用途 |
| :--- | :--- | :--- |
| **WebTransport（主）** | HTTP/3・QUIC over **UDP/443** | ゲームプレイ高速通信。**datagrams（非信頼・HOL なし）** を座標・入力・状態に、**streams（信頼）** をマッチ開始・スコア・ダメージ確定等に、1 接続で併用 |
| **WebSocket（従）** | TCP（HTTP と同系統） | チャット・ロビー・マッチメイキング、および **WebTransport 非対応/ UDP ブロック環境のフォールバック**（ゲームプレイもここに流す） |

- 接続時に WebTransport を試し、**非対応・接続失敗・UDP/443 ブロック（タイムアウト）なら即 WebSocket へフォールバック**する（WebGPU→WebGL2 と同じプログレッシブ対応の発想）。
- **NAT 越え（STUN/TURN/ICE）は不要**。クライアント→公開権威サーバーの一対多構成であり、P2P ではないため。
- geckos.io を見送る理由: ①サーバーが node-datachannel（ネイティブ）依存で **bun ランタイム互換が危険**、②**別 UDP ポート**（シグナリング 9208 等）が必要で企業/モバイル網で塞がれやすい、③WebTransport が同じ UDP の長所を 443 番・TLS1.3・NAT 設定不要で提供する。
- 参考事実: Krunker.io 自体は socket.io（WebSocket/TCP）で動作し、クライアント予測＋ラグ補償で高速感を実現している。「ブラウザFPS＝UDP 必須」ではない。

### ブラウザ/ランタイム対応（2026-09 調査）

- WebTransport: Chrome97+/Edge/Firefox114+/Safari**26.4**（2026-03 に Baseline 入り）。古い Safari・iOS WebView・UDP/443 を塞ぐ企業/ホテル Wi-Fi では不可 → **WS フォールバック必須**。
- bun: HTTP/3 を v1.3.14 で**実験サポート**したが、**WebTransport サーバー API は未実装**（bun issue #13656）。Node もネイティブ非対応（`@fails-components/webtransport` 等に依存）。

## 3. ネットワークモデル（トランスポート非依存・確定）

- **権威サーバー + クライアント予測（Client Prediction）+ サーバー調停（Reconciliation）+ ラグ補償（Lag Compensation）+ エンティティ補間（Interpolation）**。
- **サーバー固定シミュレーション tick: 60Hz**（dt = 1/60s ≈ 16.7ms 周期）。入力 60Hz と 1:1 で消費でき、命中・ラグ補償の位置履歴が密（100ms で 6 サンプル）になって当たり判定が精緻になる。BVH キネマティックは剛体ソルバ無しで軽く、20 人×60Hz でも CPU は余裕（Phase 1 で計測、定数で 30Hz にも下げられる）。
- **シミュレーション tick とスナップショット送信レートは分離する**（CS2 が 64Hz ベースでも運用するのと同じ発想）。
- **クライアント入力送信: 60Hz**（~16ms ごと、シム tick と 1:1）。入力パケットは ~12B と微小なので 60Hz でも帯域は誤差レベル、操作レイテンシが最小。
- **サーバー→クライアント状態送信: 30Hz**（20〜30Hz でクライアント/回線に応じ調整、モバイルは 20Hz 可）のスナップショット。サーバーは 60Hz でシムしつつ、送信は 1 tick おき（30Hz）にして帯域・モバイル負荷を抑える。
- **クライアント描画: 可変フレームレート（rAF = ディスプレイ 60〜120Hz+）**。ネット tick とは独立。
  - リモートプレイヤーは **補間バッファ（約 100ms）** でスナップショット間を滑らかに。
  - 自プレイヤーは**予測**で毎フレーム（delta time）動かし、サーバー確定値で**調停**。
  - 全ての移動・アニメは **delta time ベース**（フレーム時間固定を仮定しない）。シミュレーションは極端なフレーム落ちでのすり抜け防止に delta をクランプ（例: 最大 50ms）。
- **ラグ補償**: サーバーは各プレイヤーの直近 ~100ms の位置履歴を保持し、射撃イベントのクライアント時刻へ当たり判定を巻き戻す。60Hz シムなので履歴は 100ms で約 6 サンプルと密。
- **sub-tick（CS2 型）**: 射撃等のイベントは tick 境界に丸めず**クライアントの正確なタイムスタンプ**を付けて送り、サーバーがラグ補償巻き戻しで時刻順に解決する。これにより tick を 128Hz に上げずとも命中精度を確保する（送信 30Hz・シム 60Hz で十分）。
- 射撃判定: クライアントは three-mesh-bvh で**ヒットマーカーを先行表示**、サーバーが巻き戻し検証してダメージを**信頼チャネル**で確定。

## 4. メッセージ分類とプロトコル・信頼性（データ種別マトリクス）

データは性質ごとに **3 つの転送層** に分ける。ゲーム内リアルタイム通信は WebTransport を主経路とし、**非対応・UDP/443 ブロック時は WebSocket へ自動フォールバック**する（§2）。課金・認証・永続データはゲームサーバーを通さず HTTPS API を叩く。

### 4.1 超高速同期層 — WebTransport **datagrams**（非信頼・非順序、UDP 相当）

「失われても次の瞬間に最新値で上書きされるデータ」。再送せず、届いた最新だけを使う。

| データ | 方向 | 頻度 | Reliable | Ordered | 要求レイテンシ | 理由 |
| :--- | :--- | :--- | :---: | :---: | :--- | :--- |
| プレイヤー座標 / 視点 / 姿勢 | S→C | **30Hz** | ❌ | ❌ | 極小（<20ms） | 最新 1 パケットだけあればよく、過去位置は不要。HoL ブロッキングを排除 |
| プレイヤー入力（WASD / エイム / ボタン） | C→S | **60Hz**（~16ms ごと） | ❌ | ❌ | 極小（<20ms） | パケロスしても次の入力で上書き。送信は描画（可変 60〜120fps）とも独立して **60Hz**（シム tick と 1:1）。パケットは ~12B |
| アクションフラグ（`isShooting` 等のビットフィールド） | 双方向 | 状態スナップショットに同梱（30Hz） | ❌ | ❌ | 小 | 最新状態だけ必要 |

> ※ 視覚エフェクト（火花・薬莢・マズルフラッシュ等）は **datagrams で送らない**。§5 のとおり最小トリガーだけ送り、各クライアントが決定論的に再生する（パケット削減・パケロス非依存）。

### 4.2 重要イベント層 — WebTransport **streams**（信頼・順序）/ WS フォールバック

「絶対に失われてはいけないが、即時性も欲しいデータ」。datagrams とは独立した信頼ストリームで送り、位置同期を詰まらせない。

| データ | 方向 | 頻度 | Reliable | Ordered | 要求レイテンシ | 理由 |
| :--- | :--- | :--- | :---: | :---: | :--- | :--- |
| 射撃・着弾・**被弾ダメージ確定** | S→C | イベント | ✅ | ✅ | 小（<50ms） | 当たり/外れの確定は欠落厳禁。datagrams とは別ストリームで位置同期を妨害しない |
| 発射トリガー（`{playerId, seq, weapon}`） | C→S | イベント | 送信は datagram、ダメージ確定は stream | — | 小 | 射撃自体は高速 datagram、サーバー検証後の確定は信頼 stream |
| キルログ / スコアボード | S→C | イベント | ✅ | ✅ | 中 | 誰が誰を倒したかの順序・確実性 |
| テキストチャット（マッチ/ロビー） | 双方向 | 低 | ✅ | ✅ | 中 | 文字化け・順序逆転・漏れ防止 |
| ラウンド中の武器購入 / 投擲 | C→S | イベント | ✅ | ✅ | 小 | ラウンド内 State の確実な同期 |
| マッチメイキング / ルーム管理（入退室・カウントダウン・チーム分け） | 双方向 | 低 | ✅ | ✅ | 中 | 部屋状態の確実な同期。WT stream または WS |

### 4.3 Web / 決済 / 永続層 — **HTTPS API**（REST / GraphQL、CDN）

「お金・アイテム・アカウントなど、整合性と安全性が最優先のデータ」。ゲームサーバー（リアルタイム）とは分離し、専用 API + DB で扱う。

| データ | 方式 | レイテンシ | 理由 |
| :--- | :--- | :--- | :--- |
| ショップ / 課金 / ガチャ | HTTPS（REST / gRPC、HTTP/2 or /3） | 不問（200〜500ms） | **ACID トランザクション・二重決済防止（Idempotency）が最優先** |
| ログイン / 認証（JWT / OAuth） | HTTPS（REST） | 不問 | アカウント情報の安全な暗号化・トークン発行 |
| インベントリ / ロードアウト保存 | HTTPS（REST / GraphQL） | 不問 | スキン・所持アイテムの確実な DB 永続化 |
| 戦績 / ランキング閲覧 | HTTPS（REST / CDN） | 不問 | CDN キャッシュで高速読み取り配信 |
| 3D モデル / テクスチャ配信 | HTTPS（CDN） | 不問 | 大容量アセット（KTX2/GLTF）の並列・高速ダウンロード |

### 4.4 プロトコル選定の 3 原則

1. **「失われても次の瞬間に上書きされるデータ」**（位置・視点・入力）→ **WebTransport datagrams**（UDP 相当、非信頼）
2. **「マッチ中に絶対失えないが即時性も欲しいデータ」**（被弾確定・チャット・キルログ・ルーム）→ **WebTransport streams**（信頼・順序）。WT 不可環境は WebSocket
3. **「お金・アイテム・アカウント等の永続データ」**（課金・認証・インベントリ）→ **HTTPS API**（DB トランザクション・冪等性）

- 共通パケットヘッダ（ゲーム内）: `type(1B) + seq(2B) + payload`。seq により古いパケットを破棄し、WS フォールバック時の TCP HOL 待ちの影響を緩和する。
- WS フォールバック時は非信頼メッセージも信頼チャネルに流れるが、seq で古いパケットを捨てることで影響を抑える。

## 5. シリアライズ & アニメーション同期（確定）

- **高頻度パケット（入力・スナップショット）は手動バイナリ固定レイアウト（DataView / ArrayBuffer）で Phase 1 から作る**（[server-authority.md](./server-authority.md) §6）。
  - 入力 ~12B、20 人スナップショットの**アプリ payload ~330B**。MTU で見るべきは**ヘッダ込みの wire サイズ**で、payload 330 + UDP 8 + IP（IPv4 20 / IPv6 40）= **358B（IPv4）/ 378B（IPv6）**。保守 path MTU ~1200B に対し payload ≤ 1152B をアプリ上限とすれば 1 データグラムに収まる。固定小数点量子化（座標 0.01m を int16、yaw を uint16 等）とゼロアロケ（静的バッファ再利用）で GC レス・超低遅延。JSON/msgpackr は高頻度には使わない。テストでは payload と wire を別々に断言する（[server-authority.md](./server-authority.md) §6.2）。
  - **低頻度の信頼イベント（チャット・ルーム管理・購入・スコア等）は `msgpackr`** のまま（開発速度優先、JSON 感覚で使え JS 環境で最速クラス）。
  - 将来の帯域最適化（差分スナップショット・量子化強化・AOI）は必要になった段階でバイナリレイアウト上に積む。
- **アニメーション/エフェクトはネットワークに流さない（原則）**。送信するのは最小の権威状態とトリガーのみ:
  - **アクションフラグのビットフィールド**（状態スナップショットに含む）: `isShooting`（射撃中）/ `isReloading` / `isAiming`（ADS）/ `isCrouched` / `isGrounded` 等を 1〜数 bit/プレイヤーで。
  - **離散トリガーイベント**: 発射（`{playerId, seq, weapon}`）・ジャンプ・リロード開始・被弾等、seq 付きの小さいイベント。
  - **クライアント側で決定論的に再生**: マズルフラッシュ・反動（recoil）アニメ・トレーサー・薬莢排出・パーティクル・足音・銃声音は、フラグの立ち上がり／発射トリガーを受けて各クライアントがローカル再生する。
  - 移動アニメ（走る/ジャンプ/静止）は位置・速度からローカルにブレンド。
- これにより「アニメ用の transform を毎フレーム送る」必要がなくなり、パケットが大幅に削減される。

## 6. デプロイ/ランタイム構成（bun との両立）

- **Caddy（または同等の HTTP/3 対応リバースプロキシ）が HTTP/3・WebTransport を終端**し、ゲームサーバーへプロキシ。
- **bun ゲームサーバーは WebSocket とゲームロジック（権威シミュレーション）を担当**。静的配信は Caddy/CDN。
- UDP/443 が塞がれた環境はクライアントが自動で WS へフォールバック。
- bun が WebTransport サーバーをネイティブ安定サポートした段階で、エッジ終端を外して bun へ寄せる（移行時期は bun の成熟を観測して判断）。

## 7. ボイスチャット（後回し・確定）

- ゲームプレイ同期（WebTransport/WS）を先に完成させる。**ボイスは独立した後方フェーズ**。
- 方式: WebRTC **MediaStream（RTP/SRTP）** が本命（codec・ジッタバッファ・ノイズ抑制が組込み済み）。近接ボイチャなら LiveKit 等の SFU/サーバー中継（P2P ではないので TURN は原則不要、メディア用シグナリングは別途必要）。

## 8. 決定サマリ（2026-09-03）

| 論点 | 決定 |
| :--- | :--- |
| 描画 FPS | **可変（rAF = 60〜120Hz+）**。60 は全端末の下限フロアであり上限ではない。delta time ベース |
| レート構成 | **シミュレーション tick 60Hz / 入力送信 60Hz / スナップショット送信 30Hz（モバイル20Hz可）**。シム tick と送信レートは分離。全レートは shared の定数でチューニング可。射撃は sub-tick（タイムスタンプ＋ラグ補償） |
| トランスポート | **WebTransport（datagrams+streams）主 / WebSocket フォールバック**。geckos.io 不採用。STUN/TURN 不要 |
| サーバーランタイム | bun で WS＋ゲームロジック、HTTP/3/WT は Caddy エッジ終端（bun ネイティブ WT 対応後に寄せる） |
| ネットモデル | 権威サーバー＋予測＋調停＋ラグ補償＋補間 |
| シリアライズ | 高頻度（入力/スナップショット）は**手動バイナリ固定レイアウト**（~12B / ~330B、固定小数点量子化・ゼロアロケ）で Phase 1 から。低頻度の信頼イベントは **msgpackr** |
| アニメ/エフェクト | ビットフィールドフラグ（`isShooting` 等）＋発射トリガーのみ送信、**FX はクライアント決定論的再生** |
| ボイス | 後方フェーズ。WebRTC MediaStream / LiveKit（SFU） |

> **サーバー設計（ルーム規模・フレームワーク・物理・Phase 1 範囲）の確定事項は [server-authority.md](./server-authority.md) を参照。**
> 2026-09-03 追加確定: ルームは **最大 20 人/インスタンス（FFA/TDM）**、サーバーは**自前の軽量実装（bun + WS）で Colyseus は設計パターンのみ参考（ライブラリ不使用）**、物理は**自前キネマティック先行（Rapier は後から）**、**Phase 1 は WebSocket で位置同期を先行**（WT は Caddy 終端経路を検証後に有効化）。
